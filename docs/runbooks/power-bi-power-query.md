# Назначение

Этот runbook описывает путь от текущего Excel MVP к регулярной управленческой
аналитике в Power Query / Power BI без чтения raw snapshots и без записи во
внешние системы.

# Вариант 1. Регулярный Excel + Power Query

Подходит как ближайший шаг:

- расчетный слой регулярно формирует `reports/shumeyko_wb_excel_mvp.xlsx`;
- дополнительно формируются CSV-витрины командой:

```bash
.venv/bin/python scripts/export_power_bi_marts.py
```

- Power Query подключается к папке `reports/power_bi_marts/` или к отдельным
  CSV-файлам;
- консультант обновляет Excel/CSV, а Power Query обновляет управленческие
  сводки без доступа к `.env`, WB-токенам и raw-данным.

Для клиентского Power Query-комплекта используется отдельная команда:

```bash
.venv/bin/python scripts/build_power_query_client_package.py --publish-postgres
```

Она:

- читает только стабильный клиентский Excel MVP;
- выгружает плоские CSV-витрины как fallback;
- публикует эти витрины в Postgres-схему `bi`;
- формирует Excel-шаблон и M-запросы Power Query в
  `reports/power_query_client_package/`.

В базе таблицы `bi.*` используют короткие технические колонки `c001`, `c002` и
так далее, потому что длинные русские заголовки PostgreSQL обрезает. Готовые
M-запросы Power Query автоматически переименовывают колонки обратно в русские
бизнес-названия при загрузке в Excel.

Экспортируемые витрины:

- KPI периода;
- помесячная динамика;
- структура расходов;
- юнит-экономика товаров;
- возвраты;
- упущенные продажи;
- сверка с 1С ОПиУ.

Клиенту нельзя отправлять пароль в Excel. Для обновления по кнопке `Обновить
все` клиенту нужен защищенный доступ к базе: VPN, Power BI Gateway, внутренний
хост или другой согласованный канал. Учетная запись должна быть read-only и
должна видеть только клиентскую схему `bi`, а не raw snapshots.

# Вариант 2. Power BI поверх расчетных витрин базы

Это правильный следующий управленческий слой для консультантов:

- WB и 1С читаются read-only;
- факты нормализуются и считаются в расчетном слое;
- Power BI подключается не к raw snapshots, а к готовым витринам:
  `kpi_period`, `monthly_dynamics`, `expenses`, `unit_economics`, `returns`,
  `lost_sales`, `onec_opiu_reconciliation`;
- методика СПП, НДС, расходов РВБ и названий прибыли остается единой с Excel.

# Вариант 3. Web-интерфейс

Web-интерфейс остается следующим продуктовым контуром для клиентов:

- клиент выбирает период;
- смотрит дашборд и проблемные товары;
- скачивает Excel/PDF;
- не работает с Power BI-моделью напрямую.

# Методологические правила

- `Выручка после СПП` является контрольной выручкой внутри WB-методики; с
  общей выручкой 1С/ОПиУ ее не сравниваем напрямую, если в ОПиУ есть продажи не
  только Wildberries.
- `СПП` берется только из подтвержденного источника WB/1С; если источника нет,
  показывается ограничение, а не ноль без пояснения.
- До профильного налогового слоя используется `Управленческая прибыль WB`, а
  итоговый товарный показатель называется `Прибыль до налогов`, потому что это не
  полная чистая прибыль бизнеса из ОПиУ.
- Сверка с 1С/ОПиУ строится по помесячному контролю себестоимости из регистра
  продаж 1С и расходов маркетплейса из ОПиУ; расходы РВБ сначала сверяются
  общим блоком, а расшифровка по статьям используется для классификации
  расхождений.
