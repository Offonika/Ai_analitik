# Сверка финансового отчета WB с ранними Power BI-мерами

Документ фиксирует, что можно улучшить в текущем проекте Shumeyko, используя
раннюю Power BI-модель WB как ориентир. Модель Power BI не является источником
правды: текущий расчет должен следовать accepted spec
`docs/specs/wb-unit-economics-excel-mvp-implementation.md`.

# Что подтвердилось

## 1. Новый WB Finance API уже выбран правильно

Текущий проект использует новый контур:

```text
POST /api/finance/v1/sales-reports/detailed
POST /api/finance/v1/sales-reports/list
```

Это соответствует текущей документации WB. Старый метод
`GET /api/v5/supplier/reportDetailByPeriod` помечен как deprecated, а новый
метод использует camelCase-поля и строковый тип для денежных значений.

## 2. Главная формула текущего проекта сильнее старой Power BI-формулы

Старая Power BI-модель считала прибыль как набор DAX-мер:

```text
выручка
- себестоимость
- комиссия WB
- логистика
- хранение
- реклама
- налог
```

Текущий проект делает лучше:

```text
gross_profit =
  net_revenue
  - wb_commission
  - logistics
  - storage
  - acceptance
  - wb_promotion
  - penalties_and_holdbacks
  - acquiring
  - cogs_from_1c_with_extra_costs
```

После этого отдельно считается налоговый слой:

```text
vat_5_from_revenue = net_revenue * 5 / 105
usn_1_from_revenue = net_revenue * 1%
profit_after_taxes = gross_profit - vat_5_from_revenue - usn_1_from_revenue
```

Это лучше, чем старая модель, потому что:

- не называет результат полной чистой прибылью бизнеса;
- не смешивает операционные расходы ОПиУ с товарной юнит-экономикой;
- не скрывает НДС и УСН внутри одной меры;
- явно показывает статусы качества данных.

## 3. Разделение `deduction` в текущем проекте правильнее

В старой Power BI-модели удержания часто жили рядом со штрафами и доплатами. В
текущем проекте `deduction` и `deductionSum` вынесены в отдельную статью
`WB Продвижение`.

Это нужно сохранить. Иначе расходы РВБ и штрафы будут выглядеть как один общий
минус, а причины убытков по SKU будут хуже объясняться клиенту.

## 4. Хранение и продвижение лучше контролировать недельным отчетом

Power BI-модель брала хранение из строк детализации. Текущий проект делает
методологически лучше: недельные `paidStorageSum` и `deductionSum` из
`sales-reports/list` являются контрольной суммой, а товарная детализация
используется как база распределения.

Такой подход ближе к печатной форме финансового отчета WB и лучше подходит для
сверки с клиентом.

# Где текущий проект можно улучшить

## 1. Сохранять больше контрольных полей нового WB Finance API

В Power BI были полезные контрольные поля, которые не обязательно участвуют в
базовой прибыли, но нужны для диагностики:

- `forPay`;
- `ppvzReward`;
- `vw`;
- `vwNds`;
- `paymentProcessing`;
- `acquiringBank`;
- `cashbackAmount`;
- `cashbackDiscount`;
- `cashbackCommissionChange`;
- `spp`;
- `sellerPromoDiscount`;
- `loyaltyDiscount`;
- `salePricePromocodeDiscountPrc`;
- `agencyVat`.

Улучшение уже внесено: `DEFAULT_FINANCE_FIELDS` расширен, чтобы эти поля
попадали в raw payload новых выгрузок. Текущие формулы при этом не меняются.

Практическая польза:

- можно сверять `retailAmount`, `forPay`, `bankPaymentSum` и старую логику
  Power BI;
- можно объяснять расхождения по эквайрингу и комиссии WB;
- можно увидеть новые скидочные слои WB без немедленного изменения прибыли.

## 2. Добавить лист или таблицу `WB поля отчета`

Сейчас отчет показывает много сверок, но для инженерной диагностики стоит
добавить компактную таблицу по неделе/reportId:

| Поле | Зачем нужно |
| --- | --- |
| `retailAmountSum` | верхний контроль реализации по WB. |
| `cashbackDiscountSum` | контроль СПП/компенсации скидки. |
| `forPaySum` | контроль к перечислению за товар. |
| `bankPaymentSum` | контроль банковской выплаты по печатной форме. |
| `deliveryServiceSum` | контроль логистики. |
| `paidStorageSum` | контроль хранения. |
| `deductionSum` | контроль WB продвижения. |
| `penaltySum` и `additionalPaymentSum` | контроль штрафов и доплат. |

Это не должно заменять `Юнит экономику`, но сильно ускорит сверку с клиентом.

## 3. Добавить Power BI parity tests на искусственном наборе строк

Нужны тесты, которые берут маленький набор WB-строк и одновременно проверяют:

- старую Power BI-логику `Продажа - Возврат`;
- текущую нормализацию `sales_quantity`, `return_quantity`, `net_quantity`;
- `retailAmount` против `retailAmount - cashbackDiscount`, если будет принято
  новое правило СПП;
- `forPay` как контроль, но не как прибыль;
- `ppvzSalesCommission + acquiringFee + vw + vwNds + ppvzReward` как
  диагностическую расшифровку комиссии, без двойного учета.

Такие тесты помогут не спорить руками, почему раньше Power BI сходился, а
текущий отчет показывает другую классификацию.

## 4. Отдельно проверить трактовку `retailAmount` и `cashbackDiscount`

В текущей accepted-методике `net_revenue` считается выручкой после СПП, а СПП
берется из `cashbackDiscountSum` недельного списка отчетов и прибавляется для
`Выручки до СПП`.

Нужно сделать живую сверку на одном reportId:

```text
sum(detail.retailAmount)
sum(detail.cashbackDiscount)
summary.retailAmountSum
summary.cashbackDiscountSum
summary.retailAmountSum - summary.cashbackDiscountSum
```

Если окажется, что `detail.retailAmount` уже соответствует строке до СПП, тогда
нужна новая версия методики. Пока без живой сверки менять формулу нельзя.

## 5. Не возвращать старую ставку УСН из Power BI

В Power BI встречались 7% и 2%. В текущем проекте принято:

```text
НДС = revenue_after_spp * 5 / 105
УСН = revenue_after_spp * 1%
```

Это нужно оставить, пока бухгалтерия или accepted spec не зададут другую
налоговую рамку.

## 6. Не переносить рекламу в прибыль без отдельного правила

Power BI содержал блок рекламы: CTR, CPC, затраты, стоимость корзины/заказа.
Это полезно как следующий слой, но не как автоматический минус в MVP.

Перед включением рекламы в прибыль нужно решить:

- какая рекламная статистика является источником правды;
- есть ли SKU-атрибуция;
- как распределять расходы без SKU;
- как показывать статус `expense_without_sku` или `needs_review`.

## 7. Забрать из Power BI операционные идеи, но вынести их из MVP-прибыли

Полезные будущие блоки:

- ABC по выручке и маржинальному доходу;
- оборачиваемость и подсорт;
- цены и СПП;
- конкуренты;
- карточки и контент;
- план-факт.

Это хорошие страницы для web-кабинета консультанта. Они не должны усложнять
базовый Excel MVP, пока не закрыта сверка финансового отчета и 1С.

# Рекомендованный порядок работ

1. На одном свежем `reportId` построить сверочную таблицу:
   `detail sums` против `sales-reports/list`.
2. Добавить parity tests по ключевым Power BI-мерам: выручка, количество,
   возвраты, комиссия, логистика, хранение, продвижение, эквайринг.
3. После живой сверки решить, остается ли `retailAmount` текущей
   `Выручкой после СПП` или нужна корректировка через `cashbackDiscount`.
4. Добавить инженерный лист `WB поля отчета` в Excel.
5. Только после этого переносить ABC/остатки/рекламу как отдельные расширения.

# Итог

Текущий проект уже лучше старой Power BI-модели в главном: он разделяет
источники, фиксирует методику, хранит статусы качества и не прячет спорные
статьи внутри одной меры.

Главное улучшение из старой модели — не переписать формулы обратно в DAX, а
добавить больше контрольных полей и parity-сверок, чтобы доказуемо объяснять,
почему финансовый отчет WB, старая Power BI-модель и новый Excel MVP сходятся
или расходятся.
