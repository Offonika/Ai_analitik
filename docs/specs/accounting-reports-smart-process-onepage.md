# Статус документа

Это implemented ONEPAGE-контракт операционного смарт-процесса. Смарт-процесс
реализован как staff-only модуль web-кабинета этого сервиса: модель хранения,
API, Канбан, таблица, защищенные доказательства, планировщик, follow-up и audit
находятся за выключенным по умолчанию feature-флагом. Статус `implemented` не
означает, что модуль уже включен в production: условия пилота и ручная приемка
сохраняются в разделе rollout.

Первая версия работает без внешних интеграций: синхронизация с FinKoper или
другими CRM не выполняется и отнесена ко второму этапу отдельным accepted
решением. Решение также не включает автоматическую отправку клиенту,
клиентскую публикацию из кабинета, запись в 1С и автоматический расчет
зарплаты. Эти возможности требуют отдельных implementation-изменений и приемки.

# Цель

Объединить контроль закрытия месяца и ежемесячный отчет по налоговой нагрузке в
один управляемый процесс, не смешивая два самостоятельных вида отчета и их
артефакты.

Процесс должен давать руководителю однозначный ответ: оба результата
подготовлены, финальная налоговая нагрузка отправлена клиенту, доказательства
зафиксированы, а карточку можно закрыть и учесть при расчете зарплаты.

# Основания и приоритет решений

Процесс объединяет требования двух локальных исходных документов, которые не
публикуются в Git: регламента закрытия задач к зарплате и регламента отчета по
налоговой нагрузке. Первый задает создание задачи, целевой срок, проверку
руководителем и связь с расчетом зарплаты. Второй задает ежемесячную отправку,
доказательство, контрольный контакт и эскалацию.

Эта ONEPAGE является канонической для workflow и явно разрешает пересечение
сроков: пять рабочих дней считаются целевым SLA, а 15-е число следующего месяца
— жестким предельным сроком. Методики и состав показателей по-прежнему
определяются отдельными report specs и этой ONEPAGE не переопределяются.

# Ключевое решение

Одна карточка смарт-процесса соответствует уникальной связке:

```text
tenant_id + client_id + organization_id + report_period
```

Тенант и клиент сейчас связаны один к одному; `tenant_id` включен в ключ для
согласованности с правилами уникальности кабинета. `organization_id` — это
`onec_organization_id` организации клиента, `report_period` — календарный
месяц в формате `YYYY-MM` (`periodMonth` API кабинета).

В карточке автоматически создаются две связанные задачи — внутренние сущности
модуля смарт-процесса, а не записи внешнего таск-трекера:

| Задача | `report_kind` | Назначение | Клиентская отправка |
| --- | --- | --- | --- |
| Контроль закрытия месяца | `month_close_control` | Внутренняя проверка корректности закрытия | Нет |
| Налоговая нагрузка | `tax_load` | Ежемесячный клиентский отчет | Да, вручную в первой версии |

Обе задачи ведутся в одной карточке и общей ленте комментариев, но имеют
раздельные статусы, ссылки на `report_id`, файлы, замечания и подтверждения.

# Ролевая модель

На первом этапе внедрения бухгалтер и консультант считаются одним лицом —
`Ответственным специалистом`. Это сотрудник с ролью `consultant` в кабинете.
Один пользователь может подготовить данные, подтвердить бухгалтерские факты,
утвердить клиентский вывод и выполнить ручную отправку.

Подтверждение фактов и утверждение клиентского текста остаются двумя отдельными
действиями в журнале аудита, даже если у них один `user_id`. Это позволит в будущем
разделить роли без изменения процесса и истории.

Руководитель направления:

- контролирует обязательные результаты;
- утверждает исключения и отмену с `cancellation_reason=not_applicable`;
- возвращает карточку на доработку;
- подтверждает финальное закрытие к зарплате.

Руководитель направления получает отдельное разрешение
`accounting_workflow_supervisor`. Оно назначается явно и не следует
автоматически из технической роли `admin`. Поэтому руководитель может
утверждать исключения и закрытие процесса, но не получает право подтверждать
бухгалтерские факты отчетов. Пользователь с ролью `admin` может получить это
разрешение только отдельным назначением.

# Канбан и статусы

Стадии карточки имеют стабильные системные идентификаторы:

| `stage` | Название в UI | Условие перехода |
| --- | --- | --- |
| `new` | Новая | Создана карточка клиента, организации и месяца |
| `data_collection` | Сбор данных | Назначен ответственный, созданы две связанные задачи |
| `reports_in_progress` | Отчеты в работе | Формируются `month_close_control` и `tax_load` |
| `internal_review` | На проверке | Оба результата переданы на внутреннюю проверку |
| `ready_to_send` | Готово к отправке | Контроль закрытия завершен, налоговый отчет финальный и подтвержден |
| `sent_to_client` | Отправлено клиенту | Заполнены дата, канал и доказательство ручной отправки актуальной ревизии |
| `ready_for_payroll_close` | Готово к закрытию | Автоматическая проверка условий закрытия пройдена; стадия не требует отдельного ручного действия |
| `closed_payroll` | Закрыто — учтено к ЗП | Руководитель подтвердил закрытие |

Боковые стадии:

- `rework` / `На доработке` — обнаружена ошибка или клиент запросил исправление;
- `blocked` / `Заблокировано` — отсутствует обязательный источник, доступ или
  решение;
- `cancelled` / `Отменено` — карточка создана ошибочно, является дублем или
  обязательство за месяц признано неприменимым руководителем.

`closed_payroll` и `cancelled` — терминальные стадии. Возврат из
`closed_payroll` допускается только отдельным исправляющим действием
руководителя с причиной в журнале аудита; оно создает новую активную карточку,
а не переписывает закрытую историю.

Каждая из двух задач имеет собственный `task_status`:

```text
pending -> in_progress -> in_review -> completed
                         -> rework -> in_progress
pending|in_progress|in_review|rework -> blocked
blocked -> in_progress
```

Задача не может перейти в `completed` без привязанной актуальной ревизии
соответствующего `report_kind`. Для `tax_load` дополнительно обязательны два
раздельных audit-события: подтверждение бухгалтерских фактов и утверждение
клиентского текста. Отмена задачи отдельно от карточки не допускается.

Условия `completed` различаются по виду отчета:

- `month_close_control`: у current-ревизии нет source-integrity ошибки,
  рекомендация отчета равна `ready_to_close`, а ответственный зафиксировал
  `month_close_review_completed`;
- `tax_load`: current-ревизия проверена ответственным, подтверждение фактов и
  утверждение текста записаны раздельно, после чего ревизия отмечена в карточке
  как `is_final=true`.

`ready_to_close` в этом документе относится только к рекомендации внутри
`month_close_control`. Для Канбана используется отдельный stage
`ready_for_payroll_close`, поэтому отчетный статус не может случайно закрыть
всю карточку.

Переходы Канбана контролируются сервисом. Переход вперед выполняется только при
соблюдении условий целевой стадии; `ready_for_payroll_close` выставляется
автоматически
после фиксации доказательства отправки и проверки всех ограничений.
Уникальность активной карточки обеспечивается ограничением на уровне хранилища,
а не только дисциплиной пользователей.

# Представление в кабинете

Основной staff-only экран — Канбан, сгруппированный по `stage`. Карточка на
доске показывает клиента, организацию, месяц, ответственного, целевой и
предельный сроки, состояние двух задач и просрочку. Фильтры: месяц, клиент,
организация, ответственный, руководитель, стадия и наличие просрочки.

Внутри карточки доступны две задачи, общая лента комментариев, привязанные
ревизии отчетов, доказательство отправки, контрольные контакты и журнал аудита.
Табличный режим с теми же фильтрами обязателен как доступная альтернатива
Канбану; он не является отдельным процессом и использует тот же API. Каждая
колонка табличного режима сортируется локально по возрастанию и убыванию,
показывает направление и доступна для управления мышью и клавиатурой. Пустые
значения остаются внизу, сортировка не меняет данные процесса и API.

# Обязательные поля карточки

- клиент, организация 1С и календарный месяц;
- ответственный специалист и руководитель;
- ссылки на две связанные задачи;
- `report_id` и отпечаток ревизии `payloadSha256` каждого вида отчета;
- статус каждого отчета;
- признак `Предварительный` или `Финальный` для `tax_load` — флаг карточки
  процесса, а не статус отчета в кабинете;
- дата и канал отправки клиенту;
- безопасное доказательство отправки;
- результат контакта и ссылка на `follow-up`-задачу контрольного контакта;
- основание отмены и автор утверждения для
  `cancellation_reason=not_applicable`;
- журнал аудита переходов, подтверждений и возвратов на доработку.

Смарт-процесс хранит состояние процесса, безопасные идентификаторы и ссылки. Он
не пересчитывает показатели отчетов и не дублирует методики кабинета.

В контрактах отчетов v1 нет статуса «финальный»: `tax_load` ограничен
`business_status` со значениями `preliminary` и `accountant_review_required`,
а `accountant_confirmed` зарезервирован и не выставляется. Финальность и
подтверждение в первой версии — атрибуты карточки; их будущий маппинг на
`accountant_confirmed` кабинета — отдельное implementation-решение.

У ревизий отчетов нет монотонного номера версии: каждая перегенерация создает
новый `report_id`, актуальность отмечается признаком `is_current`, а
целостность ревизии проверяется по `payloadSha256`.

# Нормативные сроки

Первая версия сохраняет сроки исходных регламентов без ослабления:

- карточка и две задачи создаются не позднее последнего календарного дня
  отчетного месяца;
- целевой срок выполнения двух задач — пять рабочих дней с даты создания;
- все обязательные действия и проверка руководителя завершаются не позднее
  15-го числа месяца, следующего за отчетным;
- доказательство отправки, результат встречи и резюме контакта вносятся в
  карточку не позднее одного рабочего дня после события;
- при отсутствии ответа клиента контрольный контакт назначается ровно через
  два рабочих дня после отправки;
- если после повторного обращения связь не состоялась в течение пяти рабочих
  дней, сервис создает уведомление руководителю.

Пять рабочих дней — целевой SLA, 15-е число — жесткий предельный срок. Рабочие
дни рассчитываются по настроенному производственному календарю в часовом поясе
`Europe/Moscow`; отсутствие календаря блокирует автоматическое создание в
production, но не разрешает считать все календарные дни рабочими. Ответ или
встреча с клиентом не являются условием закрытия к зарплате.

# Контракт хранения

Минимальная модель первой версии включает следующие сущности:

| Сущность | Обязательное содержимое и ограничения |
| --- | --- |
| `accounting_workflow_cards` | UUID, `tenant_id`, `client_id`, `organization_id`, `report_period`, `stage`, `creation_kind`, ответственный, руководитель, SLA-даты, причина блокировки или отмены, `supersedes_card_id`, timestamps |
| `accounting_workflow_tasks` | UUID, `card_id`, один из двух `report_kind`, `task_status`, текущая ревизия, timestamps; `UNIQUE(card_id, report_kind)` |
| `accounting_workflow_report_revisions` | `task_id`, `report_id`, `payload_sha256`, признаки `is_final` и `is_current_for_task`, автор и время привязки |
| `accounting_workflow_deliveries` | Только для `tax_load`: ревизия, дата события, канал, безопасная ссылка на доказательство, результат контакта, автор, время аннулирования и причина |
| `accounting_workflow_followups` | Контрольный контакт, срок, статус, результат и связанное уведомление руководителю |
| `accounting_workflow_supervisors` | `tenant_id`, `user_id`, активность, кто и когда выдал или отозвал разрешение; `UNIQUE(tenant_id, user_id)` |
| `accounting_workflow_comments` | Общая лента карточки без raw source payload и секретов |
| `accounting_workflow_audit_events` | Неизменяемые события создания, переходов, назначений, подтверждений, отправки, аннулирования и закрытия |

На уровне БД действуют два ограничения:

- одна исходная карточка с `supersedes_card_id IS NULL` на
  `tenant_id + client_id + organization_id + report_period` независимо от ее
  стадии;
- одна активная карточка по той же связке, включая исправляющие карточки.

Активными считаются все стадии, кроме `closed_payroll` и `cancelled`.
`creation_kind` принимает `scheduled`, `manual_catch_up` или `correction`.
Исправляющая карточка после закрытия создается только с `creation_kind=correction`
и обязательным `supersedes_card_id`; старые строки, события и доказательства не
изменяются. Обычный повтор monthly-run возвращает актуальную карточку цепочки и
никогда не создает correction автоматически.
`supersedes_card_id` должен указывать на терминальную карточку той же уникальной
связки; циклы и ответвления correction-цепочки запрещены.

`report_id` ссылается на существующий `report_runs` того же тенанта, клиента,
организации, периода и `report_kind`. Перед привязкой сервис сверяет эти поля и
`payloadSha256`; одной проверки присланного пользователем идентификатора
недостаточно. В workflow не копируются расчетные строки и raw snapshots.

Появление новой current-ревизии не подменяет ссылку карточки молча. При любой
попытке перехода сервис повторно сверяет `is_current` и hash. Если привязанная
ревизия устарела, соответствующая задача и карточка возвращаются в `rework`, а
delivery этой ревизии аннулируется.

# Внутренний API и права

Модуль использует авторизованный API кабинета:

- список и карточка: `GET /api/accounting-workflows` и
  `GET /api/accounting-workflows/{card_id}`;
- идемпотентное создание месяца: `POST /api/accounting-workflows/monthly-runs`;
- назначение и переход: `POST /api/accounting-workflows/{card_id}/transitions`;
- привязка ревизии и действия задачи:
  `POST /api/accounting-workflows/{card_id}/tasks/{task_id}/actions`;
- отправка и доказательство:
  `POST /api/accounting-workflows/{card_id}/deliveries`;
- выдача или отзыв разрешения руководителя:
  `POST /api/accounting-workflows/supervisors`;
- комментарии: `POST /api/accounting-workflows/{card_id}/comments`.

Повтор одного запроса создания с тем же идемпотентным ключом возвращает ранее
созданную карточку и не создает новые задачи. Все изменяющие операции требуют
защиты действующей web-сессии и CSRF, проверяют tenant boundary и пишут audit.

`consultant` видит карточки доступного ему тенанта и меняет назначенные ему
задачи. Только пользователь с `accounting_workflow_supervisor` утверждает
исключение, отмену и переход в `closed_payroll`. Роли `client_*` не имеют
доступа к списку, карточкам, комментариям, вложениям и API модуля.

Выдать или отозвать разрешение руководителя может `admin`, но это отдельное
аудируемое действие и само по себе не дает `admin` права закрывать карточки.

# Автоматизация первой версии

1. Ежемесячный планировщик создает карточки по реестру активных связок
   `tenant + client + organization`; ручной запуск вызывает тот же идемпотентный
   сервис и доступен только руководителю.
2. При создании карточки формируются две связанные задачи по видам отчетов.
3. Переход в `ready_to_send` запрещен, пока не завершены обе задачи и
   `tax_load` не отмечен как финальный.
4. Предварительный отчет можно отправить только с явной пометкой
   `Предварительный`; он не закрывает обязательство по финальной версии.
5. Переход в `sent_to_client` требует даты, канала, файла или ссылки на
   финальную ревизию и доказательства отправки.
6. Если клиент не ответил в течение двух рабочих дней, создается задача
   контрольного контакта. Если связи нет еще пять рабочих дней после повторного
   обращения, руководитель получает внутреннее уведомление. Отсутствие ответа
   клиента не блокирует закрытие к зарплате.
7. Существенная ошибка или запрос на исправление возвращает карточку в
   `rework`.
8. Возврат в `rework` после отправки сбрасывает дату, канал и
   доказательство отправки; новая финальная ревизия требует повторной отправки
   клиенту.
9. Неприменимость обязательства за месяц оформляется отменой карточки с
   `cancellation_reason=not_applicable` и подтверждением руководителя. Такая
   карточка не получает статус `closed_payroll` и не считается выполненной к
   зарплате. Это решение не связано со статусом `not_applicable` отдельных
   пунктов контроля внутри `month_close_control`.

# Правило закрытия к зарплате

Карточка может перейти в `Закрыто — учтено к ЗП`, когда:

- `month_close_control` сформирован и проверен;
- финальный `tax_load` сформирован и подтвержден;
- налоговый отчет отправлен клиенту вручную;
- дата, канал и доказательство отправки сохранены и относятся к актуальной
  финальной ревизии `tax_load`;
- открытых блокирующих замечаний нет;
- исключения, если они есть, подтверждены руководителем.

Ответ или встреча с клиентом не являются условием выплаты. При отсутствии
ответа достаточно зафиксировать попытку контакта и создать задачу контрольного
контакта.

Закрытие к зарплате не отменяет уже назначенный контрольный контакт. Задача
`follow-up` и эскалация могут завершаться на закрытой карточке и дописывать
audit, не меняя ее терминальную стадию.

# Границы и безопасность

- Интеграции с 1С и источниками остаются read-only.
- Автоматическая отправка сообщений, файлов или отчетов клиенту не выполняется.
- Ручная отправка не означает клиентскую публикацию `tax_load` в web-кабинете;
  `clientPublication=false` сохраняется до отдельного accepted решения.
- Данные процесса, вложения и доказательства отправки хранятся в защищенном
  контуре сервиса рядом с отчетами кабинета; во внешние CRM, включая FinKoper,
  ничего не передается до отдельного решения второго этапа.
- Разрешенные значения `delivery_channel`: `email`, `messenger`, `meeting` и
  `other_approved`. Для `other_approved` обязателен безопасный комментарий с
  названием согласованного канала. Канал не означает, что сервис выполняет
  отправку.
- Доказательство содержит `report_id`, `payloadSha256`, время отправки,
  маскированного получателя, канал и защищенную ссылку на подтверждение. Нельзя
  сохранять пароль, токен, публичную ссылку, полное содержимое переписки или
  необработанный экспорт почтового ящика.
- Вложение проверяется по разрешенному MIME-типу и размеру, хранится вне Git и
  не выдается без повторной tenant- и role-проверки. Скриншот до загрузки
  очищается от лишней переписки и персональных данных, не относящихся к факту
  отправки.
- Секреты, токены, исходные ответы интеграций и локальные пути не попадают в
  поля карточек, комментарии и вложения.
- В первой версии карточки, audit-события и доказательства автоматически не
  удаляются. Hard-delete запрещен; политика ограниченного срока и удаления
  вводится только отдельным accepted retention-решением и не может удалять
  доказательство раньше связанного report run.
- Смарт-процесс не рассчитывает зарплату; он только формирует проверяемый статус
  для действующего процесса расчета.

# Ошибки и граничные случаи

- У активного клиента нет активной `client_companies` с непустым
  `onec_organization_id`: карточка не создается, причина фиксируется в audit
  monthly-run и показывается руководителю как пропуск реестра.
- Один из двух `report_kind` выключен в production: планировщик не создает
  частичную карточку и завершает run с явной ошибкой конфигурации.
- Производственный календарь недоступен: автоматический run прекращается до
  записи карточек; ручной запуск не подменяет рабочие дни календарными.
- Связка активирована после нормативной даты: руководитель может создать
  catch-up карточку вручную; фактическая дата не подменяется, карточка сразу
  показывает просрочку по применимому SLA.
- Генерация отчета завершилась ошибкой или без обязательного evidence: задача
  переходит в `blocked`, missing не заменяется нулем, предыдущая ревизия не
  привязывается как новая.
- Доказательство не совпадает с текущими `report_id` и `payloadSha256`, содержит
  запрещенный тип файла или не проходит tenant-проверку: запись отклоняется и
  стадия не меняется.
- Ответ клиента поступил после `closed_payroll`: результат сохраняется в
  follow-up и audit без возврата карточки в активную стадию. Запрос клиента на
  существенное исправление создает исправляющую карточку с
  `supersedes_card_id`.
- Повторный monthly-run или параллельные запросы возвращают исходную карточку
  либо актуальную карточку ее correction-цепочки; нарушение DB-ограничения
  обрабатывается как идемпотентный конфликт, а не как необработанная ошибка.

# Acceptance Criteria

- Для одной связки тенант + клиент + организация + месяц нельзя создать две
  активные карточки; уникальность обеспечивается ограничением хранилища, а не
  только регламентом.
- Monthly-run не создает новую карточку после закрытия исходной; исправление
  создается только отдельным действием с `creation_kind=correction` и
  `supersedes_card_id`.
- В каждой карточке есть ровно две связанные задачи с разными `report_kind`.
- Статус и артефакты одного отчета не закрывают задачу другого.
- Один ответственный пользователь может выполнить обе ролевые функции, но
  подтверждения фиксируются отдельными событиями в журнале аудита.
- Карточки создаются не позднее последнего календарного дня каждого отчетного
  месяца для активных связок из `clients` и `client_companies` со статусом
  `active` и непустым `onec_organization_id`.
- Пропуск обязательства оформляется только стадией `cancelled` с причиной;
  `not_applicable` требует решения руководителя и не учитывается к зарплате.
- Предварительный `tax_load` не позволяет закрыть карточку без финальной версии.
- Без доказательства отправки нельзя перейти в `ready_for_payroll_close`.
- После возврата на доработку и создания новой финальной ревизии карточка не
  может закрыться со старым доказательством отправки.
- Отсутствие ответа клиента создает задачу контрольного контакта, но не
  блокирует закрытие.
- Сервис рассчитывает целевой срок в пять рабочих дней, жесткий срок до 15-го
  числа, контрольный контакт через два рабочих дня и эскалацию через пять
  рабочих дней после повторного обращения.
- Только `accounting_workflow_supervisor` может отменить карточку, утвердить
  исключение и закрыть ее к зарплате; техническая роль `admin` сама по себе
  этого права не дает.
- Канбан и табличный режим показывают одно состояние и применяют одинаковые
  фильтры и права.
- Каждая колонка табличного режима сортируется в обоих направлениях с видимым
  и доступным состоянием сортировки.
- Автоматизация не пишет в 1С, не передает данные во внешние CRM и не открывает
  бухгалтерские отчеты клиентским ролям кабинета.

# Test Plan

- Unit: разрешенные переходы стадий и статусов задач, запрет пропуска стадий,
  терминальные состояния и создание исправляющей карточки с
  `supersedes_card_id`.
- Unit: расчет пяти рабочих дней, 15-го числа, срока контрольного контакта и
  эскалации в `Europe/Moscow`, включая выходные и праздничные дни.
- DB: уникальность исходной и активной карточки,
  `UNIQUE(card_id, report_kind)` и correction-цепочка; конкурентные и повторные
  monthly-run запросы не создают дубли после закрытия.
- Contract: к задаче можно привязать только `report_id` совпадающего тенанта,
  клиента, организации, периода и `report_kind`; `payloadSha256` сверяется.
- Workflow: `tax_load` нельзя завершить без двух audit-действий; предварительная
  ревизия и ревизия без доказательства отправки не закрывают карточку.
- Workflow: `month_close_control` со статусом `review_required` или
  `cannot_confirm` не завершает свою задачу и не смешивается с Канбан-стадией
  `ready_for_payroll_close`.
- Workflow: возврат на доработку аннулирует delivery; старая ревизия и старое
  доказательство не позволяют повторно закрыть карточку.
- Workflow: появление новой current-ревизии обнаруживается при переходе,
  возвращает задачу в `rework` и не подменяет `report_id` автоматически.
- Workflow: отсутствие ответа создает контрольный контакт и последующую
  эскалацию, но не блокирует `closed_payroll` при выполнении остальных условий.
- Authorization: `consultant`, `accounting_workflow_supervisor`, технический
  `admin` без отдельного разрешения и все `client_*` проверяются раздельно.
- Authorization: выдача и отзыв разрешения руководителя доступны `admin`,
  аудируются и не дают ему бизнес-права без отдельного назначения.
- UI: общий модуль сортировки подключен к табличному режиму, поддерживает
  клавиатуру, `aria-sort`, типизированные значения и пустые ячейки внизу.
- Isolation: список, карточка, комментарий, report revision и вложение не
  доступны из другого tenant даже по известному UUID.
- Upload: запрещенные MIME-типы, превышение лимита, публичные URL и секреты
  отклоняются; защищенное доказательство доступно только разрешенным staff.
- UI smoke: Канбан и таблица показывают одинаковые карточки, фильтры, SLA и
  состояние двух задач; действия используют тот же API.
- Boundary: планировщик, API и UI не пишут в 1С, FinKoper и другие внешние CRM и
  не выполняют автоматическую отправку клиенту.

# Rollout And Rollback

1. Реализовать модель, API, Канбан и таблицу за отдельным feature-флагом без
   включения в production. Для этого включение `tax_load` в production не
   требуется.
2. Выполнить миграцию, unit/contract/authorization тесты и dry-run monthly-run
   на тестовом контуре.
3. До production-пилота включить `tax_load` в web и воркере через
   `SHUMEYKO_ENABLED_REPORT_KINDS`, настроить производственный календарь,
   разрешение руководителя, защищенное хранилище и лимиты вложений. На момент
   принятия концепции в production включен только `month_close_control`.
4. До production-пилота отдельно подтвердить на принятом evidence, что
   `month_close_control` действительно получает рекомендацию `ready_to_close`,
   а `tax_load` может пройти подтверждение фактов и текста. Advisory-статусы
   `review_required` и `cannot_confirm` не считаются успешной приемкой.
5. Проверить один тестовый месяц на одном клиенте и организации и провести
   ручную приемку двух задач, SLA, переходов и запретов закрытия.
6. Включить ежемесячное создание ограниченной группе сотрудников.
7. Расширять внедрение только после проверки журнала аудита, изоляции вложений и
   отсутствия дублей.

Rollback отключает feature-флаг модуля и создание карточек. Созданные карточки,
задачи и журнал аудита не удаляются; отчеты в кабинете остаются доступны
сотрудникам согласно собственным флагам включения.

# Отложенные решения, не блокирующие v1

- Будущий маппинг флага `Финальный` на `accountant_confirmed` контрактов.
- Интеграция с FinKoper — второй этап, отдельное accepted решение.
- Исправление расхождения исходного регламента: имя файла содержит
  `10_04_2026`, а текст указывает дату вступления `10.04.2025`. До исправления
  используется содержание регламента, но дата не интерпретируется как новый
  срок или новая версия процесса.
- Отдельное будущее решение о клиентской публикации из кабинета.
