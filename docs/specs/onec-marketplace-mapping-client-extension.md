# Superseded

С 2026-07-08 этот spec больше не является предпочтительным способом вести
сопоставление 1С и маркетплейсов. Новый источник правды -
`docs/specs/marketplace-1c-mapping-service.md`.

Клиентское `.cfe` расширение можно использовать только как read-only источник
кандидатов или аварийный fallback. Ручные решения, статусы и audit должны
храниться в сервисе проекта.

# Goal

Пакетировать read-only HTTP-сервис сопоставления маркетплейсов и 1С в отдельное клиентское
расширение 1С, чтобы клиент мог установить один `.cfe` файл и сразу получить
стабильный endpoint для проекта юнит-экономики.

Расширение не заменяет и не изменяет расширение поставщика `ИС_Маркетплейс`.
Оно ставится поверх базы клиента и читает уже существующие регистры/справочники
расширения поставщика.

# Package Name And Artifact

Рабочее имя расширения:

```text
offonika
```

Человекочитаемое имя:

```text
offonika: экспорт сопоставления маркетплейсов и 1С
```

Артефакт поставки:

```text
offonika_<version>.cfe
```

Текущая версия после добавления Ozon-маппинга:

```text
0.2.0
```

Файл `.cfe` не хранится в Git, если он собран под конкретного клиента или
содержит клиентские параметры. В Git допустимы только spec, runbook и безопасные
текстовые шаблоны без данных клиента.

# Scope

Входит:

- отдельное расширение 1С без изменения основной конфигурации;
- HTTP-сервис `WBUnitEconomics`;
- root path `/hs/wb-unit-economics/v1`;
- методы `GET /health`, `GET /mapping` и `GET /mapping?marketplace=ozon`;
- роль только на чтение `offonika_ТолькоЧтение`;
- чтение только объектов, указанных в HTTP-service spec;
- возвращение JSON-контракта `schema_version = 1`;
- проверка установки через health и маленький mapping sample.

Не входит:

- хранение URL, паролей, WB/Ozon API tokens или других секретов внутри
  расширения;
- запись в 1С;
- изменение документов, справочников, регистров или настроек обмена;
- регламентные задания;
- UI для клиента;
- расчет себестоимости;
- чтение финансовых документов или отчетов 1С;
- публикация OData;
- изменение расширения `ИС_Маркетплейс`.

# User Roles And Business Decisions

Роли:

- инженер проекта выпускает версию расширения и changelog;
- 1С-разработчик собирает `.cfe` в Конфигураторе или EDT;
- администратор клиента устанавливает `.cfe`, публикует базу и выдает
  read-only пользователя;
- консультант проверяет, что маппинг соответствует форме сопоставления товаров
  WB или Ozon;
- проектный collector получает JSON snapshot и нормализует его в `sku_mapping`.

Бизнес-решение: для клиентов используем отдельное расширение как стандартный
способ подключения маппинга. Ручная TXT-выгрузка остается резервным путем.
Прямая публикация объектов `ИС_Маркетплейс` через OData не является
предпочтительным вариантом, потому что ее сложнее сузить до безопасного
контракта.

# Metadata Composition

В расширении должны быть только эти метаданные:

| Тип | Имя | Назначение |
| --- | --- | --- |
| Основной язык | `Language.Русский` | Ссылка на язык базовой конфигурации УНФ. |
| HTTP-сервис | `WBUnitEconomics` | Возвращает health и mapping JSON. |
| HTTP service template | `health` | `GET`, обработчик `HealthGet`. |
| HTTP service template | `mapping` | `GET`, обработчик `MappingGet`; без параметра возвращает WB, `marketplace=ozon` возвращает Ozon. |
| Роль | `offonika_ТолькоЧтение` | Минимальные права чтения. |

XML-исходник роли не должен ссылаться на объекты расширения `ИС_Маркетплейс`
через `Rights.xml`, потому что Конфигуратор 1С может не сопоставить объекты
другого расширения при загрузке из XML. После загрузки `.cfe` эффективные права
пользователя все равно должны давать чтение объектов `ИС_Маркетплейс`: либо
через ручную настройку роли в тестовой базе, если эти объекты доступны в редакторе
прав, либо через отдельную существующую read-only роль клиента.

Расширение не должно добавлять:

- справочники;
- регистры сведений;
- регистры накопления;
- документы;
- обработки с UI;
- константы;
- регламентные задания;
- планы обмена.

# Data Sources And Read Boundaries

Расширение читает:

- `РегистрСведений.ИС_WB_СоответствиеРазмеров`;
- `Справочник.ИС_WB_РазмерыНоменклатур`;
- `Справочник.ИС_WB_Номенклатура`;
- `РегистрСведений.ИС_WB_ШтрихкодыРазмеров`;
- `РегистрСведений.ИС_Ozon_СоответствиеХарактеристик`;
- `Справочник.ИС_Ozon_Номенклатура`;
- `Справочник.Номенклатура` только по ссылкам из регистра соответствия;
- `Справочник.ХарактеристикиНоменклатуры` только по ссылкам из регистра
  соответствия.

Расширение не читает:

- профили WB целиком;
- профили Ozon целиком;
- токены и настройки API;
- документы продаж, поступлений, комиссионера;
- регистры себестоимости;
- учетные записи, пароли, настройки обменов;
- raw ответы WB/Ozon.

# HTTP Contract

Расширение реализует контракт из
`docs/specs/onec-marketplace-mapping-http-service.md` с additive Ozon-полями
для `marketplace=ozon`.

Endpoint:

```text
GET /hs/wb-unit-economics/v1/health
GET /hs/wb-unit-economics/v1/mapping
GET /hs/wb-unit-economics/v1/mapping?limit=100
GET /hs/wb-unit-economics/v1/mapping?marketplace=ozon&limit=100
```

Любой метод `POST`, `PUT`, `PATCH` или `DELETE` должен возвращать отказ 1С на
уровне публикации метода. В модуле сервиса не должно быть кода записи.

# Versioning And Compatibility

Версии:

- `0.1.x`: первый контракт `schema_version = 1`, WB mapping;
- `0.2.x`: additive Ozon mapping через `marketplace=ozon`;
- `1.0.0`: первая версия после проверки минимум на одной тестовой и одной
  рабочей базе клиента.

Правила совместимости:

- удаление или переименование JSON-полей требует нового `schema_version`;
- добавление безопасного поля допускается только после обновления spec и тестов
  нормализации;
- расширение должно проверяться на базе с активным `ИС_Маркетплейс`;
- если структура `ИС_Маркетплейс` изменилась, выпускать новую patch/minor
  версию расширения.

# Security, Tenant Isolation, Audit, Retention

- В расширении нет секретов и клиентских параметров.
- Пользователь HTTP-сервиса создается в базе клиента отдельно.
- Доступ ограничивается правами 1С и, если возможно, IP allowlist.
- Логи 1С и проекта не должны содержать тело mapping response.
- Raw JSON сохраняется только локально в `data/` на стороне проекта и не
  попадает в Git/Markdown.
- Одна клиентская база = один endpoint и один набор учетных данных в runtime
  проекта.

# Errors And Edge Cases

- Расширение `ИС_Маркетплейс` не установлено: `GET /health` должен вернуть
  безопасную ошибку `marketplace_extension_missing`.
- Нет прав на регистр соответствия: `GET /mapping` возвращает `403` или
  безопасный `query_failed`, без стека и секретов.
- Структура расширения поставщика изменилась: `GET /mapping` возвращает
  `query_failed`, выпуск блокируется до адаптации запроса.
- Пустой маппинг: ответ `200` с `row_count = 0`; проект помечает source как
  `needs_review`.
- Несколько разных номенклатур 1С для одного WB товара: нормализация проекта
  ставит `ambiguous`.

# Acceptance Criteria

- `.cfe` устанавливается в тестовую базу 1С без изменения основной конфигурации.
- В расширении нет объектов хранения данных, регламентных заданий и UI.
- Роль расширения содержит только минимальные права чтения и не содержит write
  rights.
- Сервисный пользователь имеет эффективные права чтения объектов
  `ИС_Маркетплейс`, нужных для mapping.
- `GET /health` возвращает `200` и `status = ok`.
- `GET /mapping?limit=10` и `GET /mapping?marketplace=ozon&limit=10`
  возвращают JSON по контракту `schema_version = 1`.
- Ответ не содержит токены, пароли, настройки профилей, raw WB/Ozon JSON или
  финансовые документы 1С.
- Под пользователем сервиса невозможно записать объект 1С.
- Тот же mapping можно сохранить как локальный snapshot и нормализовать в
  `sku_mapping`.

# Test Plan

Перед выпуском `.cfe`:

- собрать расширение в чистой тестовой базе с активным `ИС_Маркетплейс`;
- проверить синтаксис модулей 1С;
- проверить права роли;
- вызвать `GET /health`;
- вызвать `GET /mapping?limit=10`;
- вызвать `GET /mapping?marketplace=ozon&limit=10`;
- проверить JSON на отсутствие секретных маркеров: `token`, `password`,
  `secret`, `apiKey`, `clientId`, `Authorization`;
- сравнить несколько строк с формой `Сопоставление товаров` в 1С;
- сохранить обезличенный sample структуры ответа для разработки нормализатора,
  без реальных клиентских товаров.

# Rollout And Rollback

Rollout:

1. Собрать `.cfe` с номером версии.
2. Установить в тестовую базу клиента.
3. Опубликовать HTTP-сервис и проверить health/mapping.
4. Создать read-only пользователя.
5. Ограничить доступ по IP, если доступно.
6. Подключить URL в runtime проекта.
7. Снять первый snapshot и сверить с ручной TXT-выгрузкой.
8. После приемки установить в рабочую базу клиента.

Rollback:

- отключить публикацию HTTP-сервиса;
- отключить пользователя сервиса;
- деактивировать или удалить расширение `.cfe`;
- вернуться к ручной TXT-выгрузке в `data/onec_marketplace_mapping/`;
- оставить предыдущие локальные snapshots до окончания сверки.
