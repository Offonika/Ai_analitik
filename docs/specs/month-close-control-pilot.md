# Назначение

Зафиксировать рабочий контур пилота по контролю закрытия месяца в 1С без
внедрения CRM на первом этапе.

Пилот должен показать, какие пункты клиентского регламента закрытия месяца можно
проверять онлайн через read-only доступ к 1С, какие пункты требуют файлов,
скринов или подтверждений из процессной системы, и какие вопросы остаются до
полной автоматизации.

Этот документ superseded принятой spec
`docs/specs/month-close-control-report-implementation.md`. Он сохраняет discovery
и безопасную рамку пилота. Конкретные клиентские имена, URL OData, raw-ответы,
скрины, Excel-файлы и audit pack хранятся только локально в `data/` и
`reports/`.

# Scope / Out of Scope

Входит:

- read-only чтение данных 1С через OData или другой согласованный read-only
  источник;
- онлайн-проверка ОСВ через регистр бухгалтерии/управленческого учета;
- онлайн-проверка налоговых и денежных контуров через регистры накопления;
- карта покрытия регламента: автоматом, частично, нужен файл/скрин, не покрыто;
- локальное хранение подтверждений пилота в `data/`;
- итоговый audit pack для руководителя или консультанта.

Не входит:

- запись документов, корректировок, задач или статусов в 1С;
- отправка отчетности, платежей, сообщений клиентам или действий от имени
  бухгалтера;
- полноценная CRM или замена FinKoper на первом этапе;
- хранение клиентских URL, учетных данных, raw-выгрузок или отчетов в Markdown
  документации и Git.

# Пилотная логика

Первый пилот выполняется на клиенте с ОСНО. Поэтому обязательный контур проверки:

- ОСВ за период;
- закрытие месяца;
- ЕНС и счет 68.90;
- НДС: покупки, продажи, предъявленный НДС, авансы, раздел 7 декларации при
  наличии;
- налог на прибыль и прочие налоги, если применимо;
- банк и движения денежных средств;
- ручные операции и корректировки;
- подтверждения из задачи/чата: скрины, вложения, комментарии бухгалтера,
  подтверждение руководителя.

# Онлайн-ОСВ

Целевая схема: ОСВ должна строиться онлайн из учетных движений 1С, а не
становиться регулярной ручной Excel-выгрузкой.

Приоритетный источник:

- виртуальная таблица регистра бухгалтерии/управленческого учета
  `AccountingRegister_Управленческий/BalanceAndTurnovers(...)`.

Если виртуальная таблица остатков и оборотов недоступна через OData или
возвращает неполный ответ, используется резервный онлайн-путь:

- строки регистра `AccountingRegister_Управленческий_RecordType`;
- план счетов `ChartOfAccounts_Управленческий`;
- расчет начального остатка, дебетового оборота, кредитового оборота и конечного
  остатка на стороне нашего audit pack.

Ручная выгрузка штатного отчета "Оборотно-сальдовая ведомость" допустима только
как первичная сверка, чтобы сравнить онлайн-расчет с отчетом 1С. Она не является
целевым регулярным процессом.

Для первого discovery-шагa используется отдельный probe виртуальных таблиц:

- `scripts/probe_onec_month_close_osv.py`;
- только read-only `GET`-запросы к OData;
- по умолчанию используются только уже экспортированные переменные окружения,
  без чтения `.env`;
- локальный manifest сохраняется в `data/` и содержит только статус, код ответа,
  число строк и список полей, без raw-строк, клиентских URL и секретов.

После probe audit pack выбирает источник ОСВ автоматически:

- если `BalanceAndTurnovers` доступен и полный сбор нормализуется в строки ОСВ,
  workbook использует эту виртуальную таблицу как основной онлайн-источник;
- если виртуальная таблица недоступна, падает на ошибке полного сбора или
  возвращает ненормализуемые строки, workbook использует реконструкцию по
  `AccountingRegister_Управленческий_RecordType`;
- оба сценария фиксируются в manifest и на итоговом листе Excel как фактический
  источник ОСВ.

Для реконструкции по `RecordType` основной проход читает регистр страницами. Если
лимит страниц достигнут до конца периода, audit pack пробует догрузить хвост
периода фильтром по `Period`; если конкретная база 1С запрещает такой `WHERE`,
скрипт продолжает чтение обычным `$skip` с места остановки. Manifest фиксирует
метод хвостовой догрузки, лимит страниц, факт завершения и техническую ошибку
фильтра без raw-строк, клиентских URL и секретов.

Скрипты live-доступа к 1С по умолчанию используют только экспортированные
переменные окружения `ONEC_ODATA_*` или read-only настройки 1С из личного
кабинета при явной передаче `--cabinet-client-name`/`--tenant-id`. `.env` не
читается, если оператор явно не передал `--env-file`.

Важное ограничение: если в УНФ нет бухгалтерского регистра `Хозрасчетный`, нужно
подтвердить, что штатный отчет ОСВ клиента строится из того же регистра, который
виден через OData, или согласовать другой read-only источник бухгалтерской ОСВ.

# Регистры накопления

Регистры накопления не заменяют ОСВ, но покрывают налоговую и денежную часть
регламента. Для пилота они используются по группам:

ЕНС и налоги:

- расчеты по единому налоговому счету;
- расчеты по налогам;
- расчеты по налогам на едином налоговом счете;
- расчеты по санкциям на едином налоговом счете;
- расчеты налоговых агентов и налогоплательщиков с бюджетом по НДФЛ, если
  применимо.

НДС для ОСНО:

- НДС покупки;
- НДС продажи;
- НДС предъявленный;
- НДС с авансов выданных;
- НДС с авансов полученных;
- записи раздела 7 декларации по НДС.

Деньги, банк и расчеты:

- движения денежных средств;
- денежные средства;
- оплата документов;
- оплата счетов и заказов;
- расчеты с покупателями;
- расчеты с поставщиками;
- расчеты с прочими контрагентами.

Доходы и расходы:

- доходы и расходы;
- доходы и расходы по кассовому методу;
- продажи;
- закупки.

# Процессные подтверждения

Регламент закрытия месяца требует не только учетных данных 1С, но и доказательств
процесса: скринов, вложений, факта отправки клиенту, комментариев и проверки
руководителем.

На первом этапе вместо CRM используется локальная папка пилота в `data/`.
Рекомендуемая структура:

```text
data/month_close_task_docs/<date>/
  source_docs/
  pilot_context.md
  confirmations/
    osv/
    ens/
    vat/
    taxes/
    bank/
    manual_operations/
    client_messages/
```

Если FinKoper предоставляет API, вебхуки, read-only пользователя или регулярные
выгрузки, этот источник подключается после первого пилота как процессный слой:
задачи, статусы, ответственные, вложения, чаты клиентов и проверка руководителя.

Если API нет, допустимые промежуточные варианты:

- read-only пользователь в FinKoper;
- регулярная выгрузка задач и вложений в Excel/CSV/архив;
- папка подтверждений по клиенту и периоду;
- Telegram-бот или мини-кабинет только как канал сбора подтверждений, не как
  полноценная CRM.

# Выход пилота

Audit pack должен показывать:

- период и налоговый режим;
- покрытие каждого пункта регламента;
- какие данные получены онлайн из 1С;
- какие подтверждения приложены файлами или скринами;
- какие пункты не подтверждены;
- риски и список дозапросов;
- итоговый статус: можно закрывать, нельзя закрывать, требуется проверка
  руководителем.

# Открытые вопросы

- Доступна ли `BalanceAndTurnovers` для нужного учетного регистра через OData на
  пилотной базе.
- Совпадает ли онлайн-расчет ОСВ по `Управленческий` с отчетом ОСВ в интерфейсе
  1С.
- Какой месяц берется первым для пилота.
- Какие вложения и скрины обязательны для каждого пункта регламента.
- Есть ли у FinKoper API, вебхуки, read-only доступ или регулярные выгрузки.
- Какой результат считать успешным: audit pack, чек-лист руководителя, onepage
  для заказчика или полный пакет закрытия месяца.

# Acceptance Criteria

- Пилот не требует регулярной ручной выгрузки ОСВ.
- Все обращения к 1С выполняются только на чтение.
- Клиентские URL, логины, raw-данные, скрины и Excel-отчеты не попадают в
  Markdown и Git.
- Для каждого пункта регламента есть статус покрытия.
- Для ОСВ явно указано, какой источник использован: `BalanceAndTurnovers`,
  реконструкция по `RecordType` или разовая сверочная выгрузка.
- Для процессных пунктов явно указано, какое подтверждение нужно приложить.
