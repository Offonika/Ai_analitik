# Goal

Зафиксировать первый draft для клиентского web-кабинета поверх уже принятой
Excel-методики WB/1C юнит-экономики.

Кабинет должен стать следующим продуктовым слоем после Excel MVP: клиент
открывает отчет в браузере, выбирает период и кабинет WB, видит готовые
управленческие страницы и при необходимости скачивает Excel/PDF. Excel остается
расчетным артефактом, архивом и fallback, но не единственным пользовательским
интерфейсом.

Этот документ не запускает production-разработку сам по себе. Для реализации
production backend, хранения реальных клиентских данных, авторизации и
подключения внешних систем нужен отдельный accepted implementation spec.

# Current Assets

В репозитории уже есть несколько наработок, которые можно использовать как базу:

- accepted Excel MVP spec с клиентскими листами, KPI, статусами качества данных
  и текущей методикой расчета;
- стабильный Excel workbook как источник клиентской витрины;
- генератор переносимого HTML demo dashboard из видимых листов Excel:
  `scripts/build_client_demo_dashboard.py`;
- локальные smoke tests для HTML demo dashboard, Power BI/Power Query CSV marts
  и клиентского Power Query package: `tests/test_client_demo_dashboard.py`;
- экспорт плоских витрин `reports/power_bi_marts/` через
  `scripts/export_power_bi_marts.py`;
- клиентский Power Query package через
  `scripts/build_power_query_client_package.py`;
- runbook `docs/runbooks/power-bi-power-query.md`, где web-интерфейс уже
  отмечен как следующий клиентский продуктовый контур.

HTML demo dashboard является хорошим прототипом пользовательского слоя, но пока
не является web-кабинетом: в нем нет серверной авторизации, истории отчетов,
tenant isolation, управляемого экспорта, audit log и production-хранения.

# Scope

В первый web-кабинет входит:

- просмотр готовой расчетной витрины, собранной по accepted Excel-методике;
- выбор клиента, периода и кабинета WB в рамках разрешений пользователя;
- страницы: сводка, динамика, расходы WB, убыточные товары, возвраты, упущенные
  продажи, качество данных, сверка с 1С/ОПиУ, методика;
- фильтры: период начала/окончания, месяц, кабинет WB, организация 1С, товар,
  артикул, статус данных, FBO/FBS, класс убыточности;
- экспорт текущего представления в Excel/PDF;
- ссылка на стабильный Excel MVP как расчетное приложение;
- показ ограничений периода, неполных источников и статусов качества данных;
- audit record для просмотра, экспорта и обновления отчета;
- read-only режим для WB, 1С и расчетных данных.

# Out Of Scope

Не входит в первый web-кабинет:

- запись цен, остатков, карточек или документов в WB;
- запись справочников, документов, себестоимости или корректировок в 1С;
- автоматические финансовые, налоговые, юридические или закупочные решения;
- полноценная BI-платформа и произвольный конструктор отчетов;
- замена бухгалтерии, 1С, ERP, CRM или ОПиУ;
- подключение Telegram, email, Bitrix24 и других уведомлений без отдельного
  accepted spec;
- хранение production-токенов, raw snapshots, client exports или generated
  reports в Git;
- смешивание данных разных клиентов в одной таблице без tenant boundary.

# Users And Roles

- `client_owner`: владелец или руководитель клиента. Видит все страницы своей
  компании, скачивает отчеты и смотрит управленческие выводы.
- `client_accountant`: бухгалтер клиента. Видит сверку с 1С/ОПиУ, расходы,
  методику и Excel/PDF export.
- `client_manager`: менеджер клиента. Видит товары, возвраты, убыточность,
  упущенные продажи и фильтры по ассортименту.
- `consultant`: консультант заказчика. Видит клиентов, статусы отчетов, качество
  данных, ошибки и историю запусков по своим клиентам.
- `admin`: технический администратор внедрения. Управляет доступами, источниками,
  расписанием, audit и health checks.

Клиентские роли не должны видеть raw snapshots, токены, внутренние технические
ключи и данные других клиентов.

# Screens

## 1. Client Overview

Первый экран кабинета:

- период анализа, статус периода и дата расчета;
- версия методики;
- выручка до СПП, СПП, выручка после СПП;
- продажи, возвраты, чистое количество, доля возвратов;
- расходы WB, себестоимость 1С, НДС 5%, УСН 1%;
- маржинальный доход WB после налогов;
- маржинальность WB после налогов;
- прибыльные/убыточные SKU;
- доля строк со статусом `ОК`;
- быстрые переходы к убыточным товарам, возвратам, ошибкам данных и сверке 1С.

## 2. SKU Economics

Таблица по товарам:

- неделя или месяц;
- организация 1С;
- кабинет WB;
- товар, `nmId WB`, артикул WB, артикул 1С, баркод;
- FBO/FBS;
- продажи, возвраты, чистое количество;
- выручка до СПП, СПП, выручка после СПП;
- себестоимость 1С;
- комиссия, логистика, хранение, приемка, продвижение, штрафы/доплаты,
  эквайринг;
- НДС 5%, УСН 1%;
- маржинальный доход WB после налогов;
- маржа и доход на единицу;
- статус данных и причина статуса.

## 3. Losses And Drivers

Страница убыточности:

- топ убыточных товаров;
- сортировка по маржинальному доходу WB после налогов, доходу на единицу и доле
  возвратов;
- класс убыточности: `Высокая закупка / недостаточная наценка`,
  `Возвраты + логистика`, `Прочие расходы`, `Нужна проверка данных`;
- главная причина убытка;
- фильтры по кабинету, организации, статусу и товару.

## 4. Returns

Страница возвратов:

- топ товаров по сумме возвратов;
- товары с высоким процентом возвратов;
- влияние возвратов на маржинальный доход;
- явное ограничение, если причина возврата не передается текущими источниками.

Причины возвратов можно добавить только после подтверждения read-only источника:
WB, 1С, обращения клиента или ручная классификация.

## 5. Expenses

Страница расходов WB:

- структура расходов;
- доля каждой статьи от выручки;
- динамика по месяцам;
- отдельный показ `WB Продвижение`, если он включен через недельный финансовый
  отчет, а не через отдельную рекламную методику;
- предупреждение, если статья не входит в текущую методику прибыли.

## 6. Lost Sales

Предварительная витрина упущенных продаж:

- товар, кабинет WB, артикулы и баркод;
- дни без остатка WB;
- среднедневные продажи в дни наличия;
- потенциально упущенные штуки, выручка и прибыль;
- статус источника и ограничение методики.

Эта страница не должна выглядеть как финальный прогноз спроса без отдельной
сверки с остатками 1С, календарем поставок и правилом минимального остатка.

## 7. 1C Reconciliation

Страница сверки:

- контрольные строки WB-витрины и 1С/ОПиУ;
- помесячная сверка себестоимости и расходов маркетплейса;
- дельта и комментарий;
- ссылки на Excel-листы для ручной сверки консультантом.

## 8. Data Quality

Страница качества данных:

- `ОК`;
- `missing_cost`;
- `missing_mapping`;
- `ambiguous_mapping`;
- `partial_source`;
- `needs_review`;
- `excluded`.

Строки с отсутствующей себестоимостью, маппингом, неоднозначной привязкой или
неполным источником не должны попадать в достоверную прибыль без явной пометки.

## 9. Methodology

Короткая клиентская страница:

- что считается в прибыли;
- что не входит в MVP;
- как читаются СПП, НДС 5/105 и УСН 1%;
- как работает себестоимость 1С;
- что означают статусы данных;
- почему web-кабинет не заменяет бухгалтера и 1С.

# Data Sources

Первый кабинет должен читать только готовые расчетные витрины:

- `unit_economics_report`;
- агрегаты KPI периода;
- помесячную динамику;
- структуру расходов;
- возвраты;
- упущенные продажи;
- сверку с 1С/ОПиУ;
- статус качества данных;
- `ai_analysis_summary`, если ИИ-резюме включено в accepted scope.

Кабинет не должен рассчитывать прибыль из raw API payloads на лету. Расчет
остается в deterministic calculation layer, а UI показывает уже рассчитанный
dataset с методикой и snapshot lineage.

# Architecture Options

## Option A. Static HTML From Excel

Подходит для быстрого демо:

- вход: стабильный Excel MVP;
- генерация: `scripts/build_client_demo_dashboard.py`;
- выход: один переносимый HTML без backend, CDN и внешних API;
- плюс: быстро показать клиенту будущий UX;
- минус: нет авторизации, истории, tenant isolation и управляемого обновления.

## Option B. Read-Only Web App Over Report Marts

Рекомендуемый первый продуктовый вариант:

- backend API читает только готовые report marts;
- frontend показывает готовые страницы и фильтры;
- Excel/PDF export идет из расчетной витрины;
- tenant boundary enforced in API and database;
- audit log фиксирует просмотр, экспорт и запуск обновления.

## Option C. BI / Power Query Bridge

Подходит как промежуточный управленческий слой:

- использовать `reports/power_bi_marts/`;
- Power Query или Power BI читает только клиентские витрины;
- raw snapshots, `.env`, токены и внутренние таблицы не доступны клиенту.

Этот вариант не заменяет клиентский web-кабинет, потому что UI остается ближе к
BI, а не к простому брендированному клиентскому продукту.

# Security

- Каждый клиент имеет отдельный tenant id.
- Пользователь видит только свой tenant.
- Raw snapshots, токены, `.env`, API keys и webhook URLs не показываются в UI.
- В Git не попадают реальные клиентские выгрузки, generated reports и raw data.
- Все источники WB/1С остаются read-only.
- Ошибки загрузки нельзя маскировать под пустые данные.
- Устаревший отчет нельзя показывать как свежий.
- Экспорт должен содержать период, дату расчета, версию методики и статус данных.
- Все действия, которые могут изменить внешние системы, запрещены до отдельного
  accepted spec.

# Acceptance Criteria

Draft можно считать готовым к переходу в implementation spec, если:

- подтверждено, что Excel MVP принят как методическая база;
- выбран стартовый формат: static demo, web app over marts или Power Query
  bridge;
- зафиксированы роли первого клиента;
- подтверждено, какие страницы входят в первую поставку;
- подтверждено, где хранятся расчетные витрины и generated reports;
- описан tenant boundary;
- описан read-only доступ и запрет записи во внешние системы;
- определены правила показа `partial_source`, `missing_cost`,
  `missing_mapping`, `ambiguous_mapping` и `needs_review`;
- определены export formats: Excel, PDF или оба;
- подтверждены требования к домену, white-label, РФ-хостингу, договорам и NDA;
- есть test plan до production-доступов.
