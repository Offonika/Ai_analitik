# Goal

Сформировать короткий, проверяемый и пригодный для передачи клиенту
аналитический отчёт по юнит-экономике WB. Один сохранённый `report_id` является
источником всех фактов, таблиц, выводов и ограничений документа.

Отчёт поддерживает как полный период `report_id`, так и вложенный закрытый
недельный срез. Недельный документ обязан давать отдельный управленческий
разбор каждого кабинета в форме `факт -> вывод -> действие -> сценарий`, не
подменяя доказанные данные предположениями о причинах.

```text
saved report_id
  -> report_full_payload / report_summary_for_period
  -> ClientReportModel
  -> one deterministic Markdown
  -> DOCX / PDF / HTML
```

Excel является параллельным экспортом из того же `report_id`, а не входом для
аналитического документа.

# Audience And Decision

Основная аудитория — собственник, руководитель и консультант, которым нужно за
несколько минут понять:

- итог периода и готовность данных;
- какие кабинеты и товары формируют прибыль или убыток;
- какие расходы, возвраты и остатки требуют разбора;
- какие действия подтверждаются данными, а какие остаются сценариями.

# Scope

Входит:

- единая DB-first модель клиентского отчёта;
- Markdown как детерминированный reader-facing источник DOCX/PDF/HTML;
- executive summary, KPI, помесячная динамика, кабинеты, расходы, убыточные
  товары, возвраты, упущенные продажи, качество данных, сверка с 1С, налоговый
  блок, действия, открытые вопросы и ограничения;
- отдельный детерминированный CFO-раздел логистики
  `wb-logistics-insight-v1`: executive-summary сигнал, закрытый период,
  фактический расход, доля, влияние на прибыль, стоимость на заказ/продажу,
  структура прямой/возвратной/корректирующей/нераспределённой логистики,
  недельная динамика, проблемные товары, подтвержденные действия,
  partial-границы и статусы F-1…F-5;
- доказательный управленческий разбор по каждому кабинету: главный сигнал,
  убыточные товарные группы, приоритет действий и уровень надёжности вывода;
- закрытый недельный срез внутри сохранённого `report_id` по
  `accounting_period_date`, с сохранением ссылки на исходный период и coverage;
- арифметический peer-сценарий по доле логистики только как ориентир при
  неизменных выручке и прочих расходах, а не как прогноз экономии;
- фирменный и нейтральный DOCX;
- PDF только через проверенную конвертацию готового DOCX;
- artifact hash и регистрация report-scoped файлов;
- staff draft при наличии финансовых blockers и клиентский gate через
  существующий readiness/publication контур.

Не входит:

- новые формулы юнит-экономики;
- чтение Excel или каталогов `latest` для подстановки фактов;
- прогнозирование отсутствующих периодов;
- автоматическое изменение цен, закупок, рекламы, остатков или данных 1С;
- обещание роста прибыли от одной рекомендации;
- AI-генерация чисел, причин или финансовых фактов.

# Source And Lineage Rules

- `repository.report_full_payload(db, report)` является входом для полного
  периода, а общий `report_summary_for_period` формирует вложенный период из
  того же `report_id` через фильтруемые DB-first витрины.
- `meta.reportId` обязателен; генерация без него завершается ошибкой.
- Период, coverage, методология, readiness, tax context и все строки относятся
  к одному immutable report run.
- Локальные raw snapshots, Excel workbook и «последняя» выгрузка не читаются.
- Один Markdown рендерится во все reader-facing форматы; DOCX хранит hash этого
  Markdown в свойствах документа.
- Reader-facing версия этого состава — `client-analytical-report.v5`;
  предыдущая v4 не обещает CFO-структуру логистического раздела.
- Фирменный логотип является optional presentation asset: отсутствие файла или
  запрет чтения не блокирует MD/DOCX и приводит к рендерингу без логотипа.
- Logistics-раздел строится из того же immutable report run и того же периода,
  что документ. Недельный документ использует свою закрытую неделю; полный или
  custom документ выделяет полные недели внутри выбранного окна и не смешивает
  их финансовые KPI с неполными границами.
- Вложенный недельный срез не создаёт новый финансовый факт: строки, KPI,
  расходы, возвраты и качество данных фильтруются из того же immutable
  `report_id`, а `sourceReportPeriod` и `sourceReportCoverage` сохраняются в
  metadata документа.
- Недельная сверка не наследует и не переименовывает месячную сверку WB-1С.
  Нерешённые блокеры исходного `report_id` остаются видимыми как ограничение.
- Generated artifacts остаются вне Git и доступны только через защищённый
  report-scoped API.

# Reader-Facing Structure

Порядок разделов:

1. короткий заголовок;
2. видимый `Executive Summary — краткий вывод`;
3. параметры отчёта и идентификатор `report_id`;
4. основные KPI;
5. логистика: управленческий итог закрытого периода, структура затрат,
   недельная динамика, проблемные товары, действия, partial-границы и
   ограничения F-1…F-5;
6. динамика по фактически доступным месяцам;
7. сравнение кабинетов;
8. аналитические выводы и действия отдельно по каждому кабинету;
9. структура расходов WB и топ убыточных товаров;
10. возвраты и потенциально упущенные продажи;
11. качество данных и сверка с 1С;
12. налоговые настройки 1С;
13. общие действия;
14. открытые вопросы;
15. ограничения и допущения.

В DOCX используются таблицы для точных сумм и аудита. Встроенные графики не
входят в первую версию: динамика визуализируется в web/Excel, а документ должен
оставаться воспроизводимым без отдельного графического пайплайна.

# Metric Semantics

- Клиентское название результата до налогового слоя —
  `Управленческая прибыль WB`.
- `Прибыль до налогов` показывается только когда применён налоговый слой из
  сохранённого report run.
- `Чистая прибыль` не используется.
- Нулевое отсутствующее значение не подставляется; выводится `Не рассчитано`.
- Кабинетные и товарные разрезы агрегируются только из `unitRows` текущего
  report run.
- Упущенные продажи показываются только при
  `lostSalesCoverage.calculated=true` и только за фактическое окно источника.
- Причина возврата и драйвер убытка не придумываются при отсутствии поля.
- `logisticsSharePct`, `profitEffectAmount` и финансовые рейтинги выводятся
  только для закрытого logistics analysis period. Partial-границы показывают
  фактическую логистику без финансового знаменателя.
- Logistics executive-summary и KPI-таблица используют один и тот же
  `analysisPeriod`; фактический `logisticsTotal` не смешивается с выручкой
  другого периода.
- Структура логистики выводится из `components`; доля компонента рассчитывается
  только при положительном `logisticsTotal`, а отсутствующее значение не
  подменяется нулём.
- Недельная таблица использует сохранённый `dynamics`, показывает не более
  последних 12 закрытых недель и явно сообщает о сокращении длинного периода.
- Таблица проблемных товаров детерминированно объединяет лидеров
  `byTotal`, `byRevenueShare` и `byProfitEffect`, сохраняет статус качества
  данных и не рассчитывает отсутствующие долю или влияние.

# Tax Profile Rule

- Организация, система налогообложения и ставки автоматически берутся из
  read-only настроек организации 1С и сохраняются в lineage report run.
- `taxContext.vatRate` хранится в процентных пунктах (`5` означает `5%`), а
  `taxContext.revenueTaxRate` — как коэффициент (`0.01` означает `1%`);
  генератор форматирует эти поля по разным правилам.
- Отдельное ручное подтверждение налогового режима для клиентского документа не
  требуется.
- Если настройки 1С не загружены или не применены к выбранному `report_id`,
  налоговые KPI остаются `null`; документ показывает Управленческую прибыль WB
  до налогового слоя и предлагает обновить настройки из 1С.
- Аудируемое ручное исключение может оставаться техническим fallback принятой
  налоговой методики, но клиентский документ не просит вручную подтверждать
  уже загруженные настройки 1С.

# Recommendation Rules

- Каждое действие связано с рассчитанным фактом: missing cost, mapping, loss
  rows, returns, expenses или lost sales coverage.
- В кабинетном разборе явно разделяются:
  - `Факт` — рассчитанное значение из выбранного `report_id` и периода;
  - `Ключевой сигнал` — приоритет статьи для проверки, а не доказанная причина;
  - `Действие` — конкретная проверка или отдельный сценарный расчёт;
  - `Сценарный ориентир` — арифметическая чувствительность с указанными
    неизменными условиями, а не прогноз результата.
- Для каждого кабинета выводится доля строк со статусом `ОК`, число строк
  себестоимости и mapping, требующих проверки, и уровень надёжности вывода.
- Изменение цены, скидки, закупки или продвижения формулируется как сценарий для
  отдельного расчёта, а не как обещание результата.
- Причины возвратов требуют отдельного read-only источника, если они не входят
  в report payload.
- AI может стилистически доработать отдельный staff-only client draft, но
  базовый документ всегда формируется без AI и остаётся полностью
  воспроизводимым.
- Logistics actions берутся из детерминированного insight и factor evidence.
  Статус `partial` выводится ограничением и не является оценкой экономии.

# Readiness And Access

- Consultant/admin может сформировать внутренний документ для разбора draft.
- Клиентская роль не может сформировать или скачать рекомендации при наличии
  финансового publication blocker.
- Статус `ready` и причины ограничений выводятся из текущего report payload.
- Staff-only draft checks не включаются в клиентский текст.
- Markdown, DOCX и PDF регистрируются как report artifacts с hash и размером.
- В staff-интерфейсе документ называется `Отчёт клиенту` и формируется явной
  кнопкой `Сформировать отчёт клиенту`; после успешной генерации тот же экран
  показывает прямые действия `Скачать DOCX` и, если конвертация доступна,
  `Скачать PDF`.
- В окне `Отчёт клиенту` доступны три периода:
  `Последняя закрытая неделя в текущем отчёте` (по умолчанию),
  `Весь период отчёта` и `Указать даты`. Последняя закрытая
  неделя определяется как понедельник-воскресенье, завершившиеся не позже
  `report.period_end`, и при пустом окне сервис последовательно берёт предыдущую
  полную неделю со строками. UI и API при таком откате обязаны показать
  запрошенную и фактически использованную недели; предыдущая неделя не
  называется последней без пояснения. Произвольные даты обязаны находиться
  внутри report run.
- `POST /api/reports/{report_id}/analytical-report` принимает `scope` со
  значениями `last_closed_week`, `full` или `custom`, а для `custom` —
  обязательные `periodStart` и `periodEnd`.
- Шаг `Готовый отчёт` мастера не может завершаться только текстовым сообщением:
  он показывает прямую кнопку `Скачать Excel` текущего `report_id` и действие
  подготовки отчёта клиенту без поиска в дополнительном меню.

# Acceptance Criteria

- Генератор не принимает workbook path и не читает Excel.
- В документе виден точный `report_id`, период, coverage и версия методики.
- Executive Summary расположен сразу после заголовка.
- При наличии logistics analysis Executive Summary содержит отдельный
  управленческий сигнал по логистике за тот же закрытый период.
- DOCX содержит KPI, кабинеты, расходы, убыточные товары, возвраты, lost sales,
  логистику, качество данных, налоговый блок, действия и ограничения.
- Закрытый недельный отчёт показывает точные даты недели, включает только строки
  этого окна, сохраняет исходный `report_id` и исходные period/coverage.
- По каждому кабинету есть факт, ключевой сигнал, надёжность вывода, топ-3
  убыточных товарных групп и приоритет действий.
- Если доля логистики одного кабинета минимум на 2 п.п. выше доступного peer,
  документ может показать арифметический резерв до peer-уровня только с явной
  пометкой `Сценарный ориентир, не прогноз`.
- Документ не содержит обещаний вида `прибыль вырастет в N раз` и не называет
  неподтверждённую причину расхода фактом.
- Налоговый блок прямо сообщает, что настройки взяты из 1С и отдельное ручное
  подтверждение не требуется.
- Налоговый блок показывает `vatRate=5` как `5%`, а `revenueTaxRate=0.01` как
  `1%`, без повторного умножения ставки НДС на 100.
- При отсутствующих настройках 1С нет налоговых нулей и нет текста
  `Подтвердить налоговый профиль`.
- В документе нет термина `чистая прибыль` для управленческого результата WB.
- Markdown и DOCX имеют одинаковый нормализованный текст; DOCX содержит hash
  исходного Markdown.
- HTML строится из того же Markdown и экранирует клиентские значения.
- PDF failure не создаёт пустой или stale файл и возвращает явный статус.
- Web endpoint генерирует полный или вложенный недельный/произвольный документ
  из выбранного `report_id`, возвращает фактический период и регистрирует
  артефакты.
- Logistics-раздел использует тот же период документа; для partial-границы
  финансовые показатели остаются `Не рассчитано`, а F-1…F-5 сохраняют явные
  статусы покрытия.
- Logistics-раздел содержит финансовый итог, структуру компонентов, недельную
  динамику и приоритетные товары; каждый блок отделяет факт от действия и не
  обещает неподтверждённую экономию.
- В пользовательском интерфейсе и клиентских документах результат называется
  `Прибыль до налогов`; прежнее название не отображается. Внутренние поля БД и
  API сохраняются для обратной совместимости и не меняют формулу.
- После формирования отчёта пользователь видит доступные форматы и скачивает
  файл из того же мастера; окно `Отчёт клиенту` не заканчивается пустым
  статусом `Черновик ещё не подготовлен` без следующего действия.

# Rollout And Rollback

1. Собрать новый документ для временного report run.
2. Сверить KPI, кабинеты, потери, налоговый блок и coverage с web/Excel.
3. Для недельного режима отдельно сверить число строк, даты окна и агрегаты
   каждого кабинета с фильтром web/БД.
4. Проверить DOCX и PDF визуально.
5. Переключить protected analytical-report endpoint на DB-first builder.
6. Сохранить Excel как независимый export и rollback-источник только для
   скачивания, но не для генерации текста.
7. При ошибке вернуть endpoint на предыдущую release-версию; уже опубликованный
   current report run не менять.
