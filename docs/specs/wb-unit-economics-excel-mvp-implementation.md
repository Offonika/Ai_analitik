# Implementation Status

Статус остается `accepted`. Расчетный код, Excel builder и перечисленные тесты
существуют, однако полный набор acceptance criteria, включая все live/source и
клиентские сверки, не подтверждается одной локальной тестовой командой. До
отдельной матрицы «критерий → тест или runtime evidence» повышать spec до
`implemented` нельзя.

# Назначение

Зафиксировать implementation spec для Excel MVP юнит-экономики Wildberries.
Этот spec уточняет draft `docs/specs/wb-unit-economics-mvp.md` и является
приоритетным источником правды для разработки первого технического контура.

В продуктовой рамке `AI-аналитик отчетов` этот Excel MVP является первым
проверочным слоем пилота Шумейко WB/1C: расчетная витрина и Excel-артефакт дают
фактическую базу, поверх которой консультант и AI-аналитик готовят клиентский
черновик отчета.

MVP строит воспроизводимый Excel-отчет за выбранный `report_period` поверх
фактически загруженного `source_coverage`.

`report_period` — бизнес-период отчета, заданный параметрами генератора или
`report_run`. `source_coverage` — фактически загруженное покрытие WB/1С
источников, подтвержденное snapshot manifest и lineage. Если источники покрывают
выбранный `report_period` не полностью, отчет не обрезается молча: он получает
явный статус `partial_period`, `partial_source` или `needs_review`.

Статический spec не определяет текущий опубликованный отчет. Период, покрытие,
готовность и версия методики конкретной ревизии читаются из БД по явному
`report_id`. Пилотная конфигурация поддерживает две организации в 1С и два
кабинета WB.

# Scope

Входит:

- один клиент;
- две организации 1С;
- два кабинета WB;
- управляемый `report_period`, заданный параметрами генератора или `report_run`;
- `source_coverage` WB/1С, подтвержденный snapshot manifest и `SourceLoad`;
- любой явно заданный согласованный период, поддержанный покрытием источников;
- если выбранный период не закрыт или источники покрывают его не полностью,
  статус периода явно показывает ограничение;
- смешанная модель WB: FBO и FBS;
- недельная динамика, неделя понедельник-воскресенье;
- месячная динамика по месяцам выбранного `report_period` с явной пометкой
  неполных месяцев;
- для месячного P&L недельная строка WB относится к учетному периоду по
  фактической дате сопоставленного проведенного документа 1С
  (`accounting_period_date`). Неделя `27.04.2026–03.05.2026`, проведенная
  отчетом комиссионера от `30.04.2026`, относится к апрелю. Операционные
  `week_start`/`week_end` сохраняются отдельно и не подменяют дату документа;
- если проведенный документ 1С не найден или найден на нескольких разных
  датах, строка сохраняет явный `accounting_period_source` со значением
  `wb_week_end_fallback` или `onec_document_date_ambiguous`; для совместимости
  период определяется по `week_end`, но такое происхождение не считается
  подтвержденной синхронизацией с 1С;
- WB source coverage начинается с понедельника первой недели, чье воскресенье
  входит в `report_period`; апрель требует raw coverage с 30.03.2026, а строки
  включаются только при `report_period_start <= week_end <= report_period_end`;
  `wb_finance_detail.payload.sourceCoverageStart/sourceCoverageEnd` фиксируют
  расширенное raw-окно отдельно, при этом период `report_run` не изменяется;
- штрафы WB показываются в P&L полной суммой документа и не участвуют в
  пропорциональном распределении входного НДС по услугам; если строка штрафа
  в приходной накладной 1С имеет `СуммаНДС = 0`, её сумма после перехода к
  P&L без НДС не уменьшается;
- timezone `Europe/Moscow`;
- себестоимость из 1С, включая распределенные допрасходы;
- маппинг WB <-> 1С из собственного сервиса сопоставления проекта;
- эквайринг WB;
- налоговый слой по товарам: расчет по налоговому профилю организации 1С;
- явные статусы качества данных;
- Excel workbook как основной артефакт приемки;
- клиентский Markdown/DOCX черновик аналитического отчета поверх
  рассчитанной витрины;
- предварительная витрина `Упущенные продажи` по историческому WB
  `STOCK_HISTORY_DAILY_CSV`: дни без остатка WB, среднедневные продажи в дни
  наличия, остатки 1С по складам, потенциально упущенные штуки, выручка и
  прибыль;
- отдельный клиентский лист `Сверка с 1С ОПиУ`: основная помесячная сверка
  себестоимости из WB-расчета с отчетом `Валовая прибыль 1С` по дате документа,
  расходы РВБ с ОПиУ, а также справочные строки ОПиУ по выручке, СПП, НДС,
  маржинальному доходу WB и чистой прибыли 1С/ОПиУ;
- опциональный лист `ИИ-резюме`.

Не входит:

- самостоятельный расчет рекламы WB как отдельной статьи вне недельного
  финансового отчета;
- web-кабинет;
- уведомления в Telegram, email, Bitrix24;
- production-хранение реальных клиентских данных;
- запись в WB, 1С, банк, CRM или другие внешние системы;
- подключение других маркетплейсов.
- распределение прочих переменных расходов ОПиУ вне налогов и WB-расходов:
  агентские, транспорт, аренда, маркировка и другие статьи будут добавлены
  отдельным правилом после согласования баз распределения.
- финальная прогнозная модель спроса и поставок для упущенных продаж без сверки
  с 1С остатками комиссионера, календарем поставок и согласованным правилом
  минимального остатка.

# Источники данных

Основной источник финансового факта WB: `WB Finance / Financial Reports`.
Для первого реального MVP используется новый read-only метод:

- `POST https://finance-api.wildberries.ru/api/finance/v1/sales-reports/detailed`;
- период запроса задается параметрами source refresh и фиксируется в snapshot
  manifest;
- `period=daily`;
- `limit <= 100000`;
- пагинация по `rrdId`: первый запрос с `rrdId=0`, затем `rrdId` последней
  строки предыдущего ответа, до ответа `204 No data`;
- лимит текущей документации: 1 запрос в минуту на кабинет продавца;
- токен: Personal или Service token с категорией Finance.

Для сверки недельных итогов без товарной детализации дополнительно используется
read-only метод:

- `POST https://finance-api.wildberries.ru/api/finance/v1/sales-reports/list`;
- `period=weekly`;
- `limit <= 1000`;
- лимит текущей документации: 1 запрос в минуту на кабинет продавца;
- поле `deductionSum` выводится отдельной статьей `WB Продвижение / удержания`.

Для точной детализации уже известных недельных отчетов WB можно отдельно
догружать read-only метод:

- `POST https://finance-api.wildberries.ru/api/finance/v1/sales-reports/detailed/{reportId}`;
- вход: один или несколько недельных `reportId` из `sales-reports/list`;
- пагинация по `rrdId` такая же, как у детализации за период;
- лимит текущей документации: 1 запрос в минуту на кабинет продавца;
- этот путь нужен, чтобы в Excel показывать понятные пользователю недельные
  reportId, например отчет комиссионера и уведомление о выкупе, а не только
  технические дневные `reportId` из периодной выгрузки.

Для сопоставимой денежной сверки выкупов source refresh дополнительно загружает
только для чтения первичные документы WB:

- `GET https://documents-api.wildberries.ru/api/v1/documents/list` с категорией
  `redeem-notification` и периодом отчета;
- `GET https://documents-api.wildberries.ru/api/v1/documents/download` для ZIP
  выбранного уведомления;
- из XLSX внутри подписанного архива извлекаются только итоговые поля
  `Количество`, `Сумма выкупа, вкл. НДС` и `Сумма НДС`;
- source row связывается с кабинетом и недельным `reportId`, содержит hash
  первичного архива и Decimal-значения строками;
- токен обязан иметь категорию `Документы`. Ошибка `401/403` является
  `needs_review` только для этого optional-источника и не превращает отсутствие
  первички в нулевую сумму.

Для товарной базы распределения хранения используется read-only paid storage
report:

- `GET https://seller-analytics-api.wildberries.ru/api/v1/paid_storage`;
- недельный период понедельник-воскресенье помещается в лимит WB: не больше 8
  дней;
- метод создает задачу, статус читается через
  `/api/v1/paid_storage/tasks/{task_id}/status`, результат через
  `/api/v1/paid_storage/tasks/{task_id}/download`;
- токен: Analytics;
- поле `warehousePrice` используется как сумма строки хранения по `nmId`.

Для товарной базы распределения `WB Продвижение` можно использовать read-only
статистику рекламных кампаний:

- `GET https://advert-api.wildberries.ru/adv/v1/promotion/count` для списка
  кампаний;
- `GET https://advert-api.wildberries.ru/adv/v3/fullstats`;
- период запроса не больше 31 дня;
- используются кампании в статусах `7`, `9`, `11`;
- поле `days[].apps[].nms[].sum` используется как сумма расхода по `nmId`.

Эти два API не задают итоговую сумму периода в Excel. Они являются только
товарной базой распределения. Финальная сумма хранения и `WB Продвижение`
всегда берется из недельного финансового отчета WB:
`paidStorageSum` и `deductionSum`.

Для текущего среза остатков WB подключается read-only отчет складских остатков:

- `GET https://seller-analytics-api.wildberries.ru/api/v1/warehouse_remains`;
- метод создает задачу, статус читается через
  `/api/v1/warehouse_remains/tasks/{task_id}/status`, результат через
  `/api/v1/warehouse_remains/tasks/{task_id}/download`;
- токен: Analytics;
- snapshot сохраняется в `data/wb_warehouse_remains/<timestamp>/` как raw JSON
  и `manifest.json`;
- группировка при выгрузке: артикул продавца, `nmId`, баркод, размер и склады;
- это текущий срез остатков WB, а не исторический ряд за апрель-май-июнь.

Для исторического ряда остатков WB подключается read-only Seller Analytics CSV:

- `POST https://seller-analytics-api.wildberries.ru/api/v2/nm-report/downloads`;
- `reportType=STOCK_HISTORY_DAILY_CSV`;
- текущий загруженный stock-history source coverage: `2026-04-01` —
  `2026-06-17`; для другого `report_period` требуется отдельная выгрузка или
  явный статус неполного покрытия;
- `stockType=wb`, то есть история остатков по складам WB;
- статус читается через `GET /api/v2/nm-report/downloads` с
  `filter[downloadIds]`;
- ZIP с CSV скачивается через
  `GET /api/v2/nm-report/downloads/file/{downloadId}`;
- snapshot сохраняется в `data/wb_stock_history_daily/<timestamp>/`;
- этот источник можно использовать как базу для витрины дней без остатка и
  оценки упущенных продаж.

Старый метод `GET /api/v5/supplier/reportDetailByPeriod` не используется как
основной путь, потому что по release notes WB текущая версия будет отключена
15 июля 2026 года. Его можно использовать только как временный диагностический
референс для сопоставления полей, если новый endpoint недоступен у конкретного
токена.

Официальные страницы, которые нужно проверять перед реализацией и при изменениях
WB API:

- `https://dev.wildberries.ru/docs/openapi/financial-reports-and-accounting`;
- `https://dev.wildberries.ru/docs/openapi/reports`;
- `https://dev.wildberries.ru/docs/openapi/promotion`;
- `https://dev.wildberries.ru/docs/openapi/wb-tariffs`;
- `https://dev.wildberries.ru/docs/openapi/analytics`.

Operational Reports и Analytics можно использовать только как вспомогательные
источники для сверок, идентификаторов, остатков или операционной диагностики.
Финансовые суммы отчета должны опираться на WB Finance, если доступ и поля
доступны по текущей документации.

Для детализации товаров и маппинга используется read-only метод WB Content
`POST /content/v2/get/cards/list`. Если финансовый отчет содержит товары,
которые уже убраны из активных карточек, можно дополнительно читать
`POST /content/v2/get/cards/trash`. Эти методы нужны для идентификаторов
карточек и не являются источником финансового факта.

# Decisions

- `report_period` задается параметрами генератора или `report_run`, а не
  выводится автоматически из WB snapshot manifest.
- `period_start` и `period_end` в manifest WB Finance описывают
  `source_coverage`: какие даты реально загружены из источника.
- Сборка должна проверять, покрывает ли `source_coverage` выбранный
  `report_period`. Если покрытие неполное, отчет получает явный статус
  `partial_period`, `partial_source` или `needs_review`; нельзя молча считать
  непокрытые даты нулевыми.
- Статус и фактические даты опубликованного отчета определяются только его
  `report_run`; даты не дублируются как текущие в этом spec.
- Период `2026-04-01` — `2026-06-17` остается доступным через параметры
  генератора для сравнения с предыдущей версией отчета или отдельного
  коммерческого среза.
- Если отчет строится до закрытия выбранного `report_period`, статус периода:
  `partial_period`.
- После закрытия периода и загрузки всех источников отчет может иметь статус
  `final`.
- По умолчанию `WB_ACCOUNT_1 -> 1C_ORG_1`, `WB_ACCOUNT_2 -> 1C_ORG_2`.
- Маппинг можно переопределить конфигурацией без изменения кода.
- Эквайринг включается в формулу прибыли.
- Если эквайринг недоступен из WB, отчет получает `partial_source` или
  `needs_review`; нельзя молча считать прибыль без эквайринга.
- Возвраты относятся к периоду WB Finance.
- Дата исходной продажи, если доступна, хранится справочно.
- Реклама маркируется `excluded_from_mvp` и не вычитается из прибыли.
- `ИИ-резюме` опционально и не блокирует приемку MVP.
- Причины возвратов не выдумываются: если текущие источники не передают
  подтвержденную причину, в Excel и отчете выводится ограничение источника.
- В текущем Excel MVP строится предварительная витрина упущенных продаж на базе
  `STOCK_HISTORY_DAILY_CSV`: дни с нулевым остатком WB умножаются на
  среднедневные продажи в дни наличия и среднюю выручку/прибыль на проданную
  единицу за период.
- Production-сборка передает в отчет только snapshot stock-history из того же
  `source_refresh_run`; неявный выбор последнего локального каталога запрещен.
- WB предоставляет `STOCK_HISTORY_DAILY_CSV` максимум за последние три
  календарных месяца. Collector сохраняет полный запрошенный `report_period`
  и фактическое окно провайдера отдельно; дни до доступного окна остаются
  непокрытыми и не дополняются старым snapshot.
- Расчет выполняется по кабинету только когда manifest и дневные колонки
  полностью покрывают `report_period`. Дата вне покрытия или отсутствующая
  колонка имеет статус `unknown`, а не нулевой остаток. При неполном покрытии
  агрегат получает `not_calculated`, а витрина показывает число покрытых дней.
- Канонический результат называется `Оценка недополученного маржинального
  дохода до налогов`. Товары с отрицательным маржинальным доходом исключаются
  из этого агрегата и выводятся как `Предотвращенный убыток / не пополнять`.
- Предварительная витрина упущенных продаж является управленческим рейтингом для
  проверки пополнения, а не финальным прогнозом спроса; перед управленческими
  решениями ее нужно сверить с 1С остатками комиссионера и графиком поставок.
- Остатки комиссионера из 1С можно использовать как сверочный контур для
  случаев, когда товар числится у комиссионера/на маркетплейсе в 1С, но
  отсутствует или недоступен на складах WB.
- Остатки 1С по складам выводятся в строках листа `Упущенные продажи`: если
  товар имеет дни без остатка WB, положительную потенциальную прибыль и
  положительный складской остаток 1С, управленческий вывод должен указывать на
  перемещение собственного остатка на WB. Эти остатки не заменяют историю WB и
  не превращают витрину в финальный прогноз спроса.

# Data Flow

```text
WB Finance API
  -> raw snapshots
  -> local Postgres raw/detail facts
  -> normalized wb_api_snapshot
WB Content Product Cards API
  -> raw product card snapshots
  -> flat mapping candidates
1C OData sample / export / fixture
  -> onec_unf_cost_snapshot
  -> sku_mapping
  -> local Postgres calculation input snapshots
account_org_mapping
  -> unit_economics_report
  -> Excel workbook
  -> optional ai_analysis_summary
```

Первый технический контур для 1С использует read-only OData sample-export или
локальный обезличенный fixture. OData-доступ выполняется только `GET`-запросами и
сохраняет raw sample в локальный `data/` для последующей нормализации и сверки
методики. Реальные клиентские выгрузки не входят в Git и Markdown.

Локальный Postgres используется как промежуточный слой фактов для повторяемой
сборки отчетов из уже скачанных snapshots. Таблица
`wb_unit_economics.wb_finance_detail_raw` хранит:

- полный исходный объект строки WB в `row_payload jsonb`, чтобы не терять новые
  или редко используемые поля API;
- typed-колонки для основных идентификаторов, дат, недели, `nmId`, `sku`,
  артикула, операции и сумм;
- `snapshot_id`, `source_file`, `row_number`, `raw_payload_hash` для
  воспроизводимости и идемпотентной повторной загрузки;
- `is_partial_source`, если manifest не дошел до `204 No data` или один из
  кабинетов завершился ошибкой.

Текущий WB Finance запрос выполняется с `period=daily`; недельность для отчета
формируется в Postgres через `week_start`/`week_end` и представление
`wb_unit_economics.v_wb_finance_weekly_totals`.

После нормализации локальных файлов Postgres также хранит расчетные входы:

- `wb_unit_economics.sku_mapping_snapshot` для версии маппинга WB <-> 1С;
- `wb_unit_economics.onec_cost_snapshot` для версии себестоимости 1С.

Эти таблицы загружаются из локальных read-only snapshots и не выполняют запись в
WB или 1С. Повторная загрузка того же `snapshot_id` идемпотентна по стабильным

## `tax_profile`

Поля:

- `client_id`;
- `organization_id`;
- `tax_system`: налоговый режим организации 1С;
- `vat_rate`: ставка НДС в процентах;
- `vat_mode`: `included`, `excluded` или `none`;
- `vat_deduction_mode`: право принимать входящий НДС к вычету:
  `allowed`, `not_allowed`, `not_applicable` или `unknown`;
- `revenue_tax_rate`: расчетная доля налога с выручки, например `0.01`;
- `income_tax_kind`: вид налога на доход, например `ip_ndfl_progressive`;
- `valid_from`;
- `valid_to`;
- `source`: явный read-only источник 1С либо `manual_override`; `fixture`
  допустим только в тестах.

Профиль используется только как правило расчета ставок в товарной
юнит-экономике. Фактически начисленные или уплаченные налоги 1С не
распределяются по SKU и остаются сверочным контуром.

Источник профиля — read-only настройки и учетные факты 1С. Приоритет источников:

1. явные налоговые реквизиты `Catalog_Организации` или действующего
   `Document_УведомлениеОСпецрежимахНалогообложения`;
2. согласованный набор фактических регистров 1С: вид налога из проведенного
   `Document_НачислениеНалогов` и его табличной части, ставка НДС из
   `AccumulationRegister_НДСЗаписиКнигиПродаж_RecordType`, а также признак
   включения НДС в стоимость из карточки организации;
3. действующее аудируемое исключение организации — только для реквизита,
   который стандартная OData-публикация 1С не отдает напрямую.

Фактический вид налога `Налог при УСН (доходы)` подтверждает систему и объект
налогообложения, но сумма начисленного налога не используется для обратного
вычисления ставки: она может быть уменьшена на страховые взносы. Ставка НДС 5%
или 7% считается подтвержденной только по активным записям книги продаж за
период. Для специальных ставок НДС при УСН входной НДС не принимается к вычету;
это правило фиксируется как `not_allowed`. Если карточка организации содержит
`НДСВключатьВСтоимость=true`, используется `vat_mode=included`.

Если точная ставка УСН отсутствует в OData, допускается один сохраняемый
аудируемый якорь ставки по конкретной организации и периоду. При каждом новом
source refresh система заново подтверждает в 1С систему, объект и НДС и
использует якорь только при совпадении системы, объекта и периода. Изменение или
конфликт фактических данных 1С отключает автоматическое разрешение профиля и
дает `needs_review`; старый профиль не наследуется молча.

Для ИП в периоде 2026 профиль ОСНО 22% может быть получен автоматически из
совместного набора учетных признаков карточки организации: тип
`ФизическоеЛицо`, непустой счет личных средств предпринимателя, общая ставка
НДС, `НДСВключатьВСтоимость=false` и успешно загруженный полный источник
уведомлений о спецрежимах без действующего спецрежима. Источник фиксируется как
`Catalog_Организации:derived_osno_2026`; НДФЛ по SKU не распределяется.
Если нужные поля 1С не опубликованы через OData, production-расчет получает
`missing`. Единственный допустимый fallback — временное ручное исключение с
автором, причиной, датами действия и audit-записью. Профиль нельзя назначать на
весь `client_id`, потому что у одного клиента могут быть разные организации 1С
с разными налоговыми режимами. Поле учета страховых взносов не является
доказательством УСН, а отсутствие уведомления о спецрежиме само по себе не
доказывает ОСНО.
Фактические поля `Catalog_Организации` `ВидСтавкиНДСПоУмолчанию` и
`НДСВключатьВСтоимость` сохраняются только как диагностика источника. Значения
`Общая` и `БезНДС` не являются доказательством соответственно ОСНО или УСН и
не определяют право на вычет. Коллекция `onec_tax_profiles` показывает по
каждой организации опубликованные и отсутствующие обязательные налоговые поля,
чтобы различать ошибку загрузки и ограничение публикации OData.
Если `vat_deduction_mode = unknown`, клиентская витрина не называет НДС
`к вычету`, не рассчитывает налоговые KPI и показывает налоговый контекст как
неподтвержденный. То же правило применяется к неподдерживаемому объекту налога,
включая УСН `Доходы минус расходы` до появления отдельной принятой методологии
расходов и минимального налога. Старые профили получают `unknown` без изменения
сохраненных отчетов.

Синхронизация профиля и применение профиля — разные состояния. Живой профиль
сразу сохраняется в PostgreSQL, но существующий report run не меняется. Его
налоговый слой считается примененным только если report rows рассчитаны с
профилем и `SourceLoad` содержит тот же snapshot hash `onec_tax_profiles`.
Изменение профиля создает новый staff draft; опубликованный отчет остается
immutable до отдельной приемки и публикации.

Для штатной DB-first пересборки налоговые профили не читаются повторно из
произвольного локального каталога после синхронизации source refresh. Сервис
разрешает профиль каждой активной организации на весь `report_period` из
профилей именно текущего source refresh и действующих аудируемых ручных
исключений, затем передает полученный список в deterministic calculation.
Пустой список передается явно и означает обязательный, но отсутствующий
профиль; старый отчет или профиль предыдущего refresh не используется как
fallback. Строки отчета, tax-profile collection и публикационный gate обязаны
показывать один и тот же effective source (`1C`, `manual_override` или
`missing`).

Публикационный gate проверяет профиль целевого draft по каждой организации и
всему периоду отчета. Текущий опубликованный отчет не является источником
налогового режима для нового draft: подтвержденный переход ОСНО → УСН не
наследует старые ОСНО-проверки. Если профиль отсутствует, не покрывает период,
имеет `vat_deduction_mode = unknown`, строка рассчитана без профиля либо методика
режима не поддержана, `readiness.blockingReasons[]` получает аддитивный код
`tax_profile_unconfirmed`, а `publish_report` не переключает current report.
Исключение допускается только через отдельную аудируемую staff-операцию
`publish-with-tasks` с явным подтверждением и причиной: она не рассчитывает
отсутствующие налоги, сохраняет блокеры как канбан-задачи и не разблокирует
клиентские финансовые рекомендации.

Явно сохраненная в настройках организации ставка с автором, причиной и периодом
действия является подтвержденным расчетным реквизитом. Она применяется в staff
draft и при обычной публикации без отдельного документа-основания. Поля
`rate_basis_kind`, `basis_document`, `confirmed_by` и `source_object_ids` можно
хранить как дополнительную аудиторскую справку о региональной льготе, но их
отсутствие не создает блокер и не переводит примененный налоговый профиль в
состояние `Не подтвержден`.

Сводный API отчета различает валовую выручку и выручку без НДС. Поля
`kpis.revenueWithVat`, `kpis.revenueWithoutVat`, `kpis.vatOutput`,
`kpis.revenueTax`, `kpis.totalTax`, `kpis.profitBeforeTax`,
`kpis.profitAfterTax`, `kpis.marginAfterTax` и `kpis.taxBridgeCalculated`
образуют проверяемый налоговый мост. `marginAfterTax` равен
`profitAfterTax / revenue_for_pnl`: для ОСНО знаменателем является выручка без
НДС, для остальных режимов — база выручки применённого профиля. При нулевой
выручке, неприменённом профиле или несходящемся мосте поле равно `null`, а не
нулю. `totalTax` остаётся полной справочной суммой налоговых обязательств; для
ОСНО НДС не входит в товарный P&L, поэтому налоговый мост вычитает только налоги,
включённые в P&L, и не вычитает НДС повторно. Пока НДФЛ ИП не распределён по
SKU, `profitAfterTax` является результатом юнит-экономики с явной оговоркой, а
не полной чистой прибылью бизнеса. Legacy-поля сохраняются для обратной
совместимости, но web UI не использует их для подписей УСН/НДФЛ.

Текущая гипотеза discovery: `AccumulationRegister_Запасы` является основным

стоимость по движению или другая логика. До подтверждения заказчиком такая
себестоимость имеет статус `needs_review`.

Первый OData sample показывает, что строки `AccumulationRegister_Запасы`
приходят на уровне регистратора с вложенным `RecordSet`. Для нормализации нужно
разворачивать вложенные строки и сохранять минимум:

- `Recorder`;
- `Recorder_Type`;
- `LineNumber`;
- `Period`;
- `RecordType`;
- `Active`;
- `Номенклатура_Key`;
- `Организация_Key`;
- `Характеристика_Key`;
- `Партия_Key`;
- `Количество`;
- `Сумма`;
- `СуммаБезНДС`;
- `ФиксированнаяСтоимость`.

Provisional-правило до согласования с заказчиком: фиксированные стоимостные
приходные строки с ненулевым количеством можно использовать как кандидат на
стоимость единицы по номенклатуре, организации и характеристике. Расходные
строки без количества нельзя напрямую превращать в unit cost; их нужно держать
для сверки сумм списания и отдельной проверки методики. Выбор `Сумма` или
`СуммаБезНДС` зависит от согласованного учета НДС.

После расширения OData основной кандидат для себестоимости проданных товаров —
`AccumulationRegister_Продажи`. Если сборка отчета получает
`--sales-register-dir` или находит свежий `sales_register.raw.json` под
`data/onec_gross_profit_samples/`, нормализатор читает регистр продаж,
разворачивает вложенный `RecordSet` и сначала собирает себестоимость по
документу 1С внутри недели. Затем недельная себестоимость считается только по
документам, где есть ненулевое количество:

```text
document_unit_cost =
  sum(abs(Себестоимость или СебестоимостьБезНДС) внутри документа)
  / sum(abs(Количество) внутри документа)

week_unit_cost =
  sum(document_cost for documents with quantity)
  / sum(document_quantity for documents with quantity)
```

В реальном OData sample количество и себестоимость могут приходить разными
строками одного регистра: строки с `Количество` заполняют объем, а строки с
`Себестоимость`/`СебестоимостьБезНДС` могут иметь нулевое количество. Поэтому
агрегация суммирует количество и выбранное поле себестоимости отдельно внутри
одного документа, а не отбрасывает строки с нулевым количеством. Но суммы
закрытия месяца или корректировок по другим документам без количества не
переносятся на документ с продажами и не раздувают его цену единицы.

В товарной витрине сумма себестоимости считается по знаковому количеству WB:
`cogs = unit_cost * quantity`, где продажа имеет положительное количество, а
возврат отрицательное. То есть продажа увеличивает себестоимость, а возврат
уменьшает ее на ту же единичную себестоимость для соответствующей недели,
организации и номенклатуры.

Себестоимость из регистра продаж действует только на неделю движения 1С. Это
нужно для сверки с отчетом `Валовая прибыль по номенклатуре`: средняя
себестоимость за весь квартал не используется как основной расчет, потому что
дает расхождения по конкретной неделе и документу.

Если для недели продажи WB в регистре `Продажи` еще нет себестоимости, но по
этому же товару, организации и характеристике есть себестоимость в другой
неделе, расчет использует ближайшую доступную себестоимость. Сначала выбирается
ближайшая прошлая неделя, затем ближайшая будущая. Такая строка попадает в
расчет прибыли, но получает статус `needs_review`, потому что после закрытия
месяца ее нужно сверить с финальной себестоимостью недели продажи.

Для расчета WB-себестоимости из регистра продаж используются оба независимых
еженедельных пакета РВБ/WB. Строки `reportType=1` получают недельную стоимость
единицы только из документа 1С `ОтчетКомиссионера`, а строки `reportType=2` —
только из соответствующей `РасходнаяНакладная` по выкупу. Если точного
стоимостного слоя нужного типа нет, разрешен fallback на другой подтвержденный
слой того же товара и недели только со статусом `needs_review`. Обычные продажи
1С, даже если они попали в `AccumulationRegister_Продажи` по той же организации
или контрагенту, не участвуют в себестоимости WB-витрины.

Отдельный календарный показатель `Себестоимость продаж 1С` не пересчитывается
по количеству WB. Он равен прямой сумме поля `Себестоимость` регистра
`AccumulationRegister_Продажи` по фактической дате проведения, выбранной
организации и кабинету. В него входят `ОтчетКомиссионера`,
`РасходнаяНакладная` по выкупу и стоимостные корректировки
`ЗакрытиеМесяца`. Рядом отдельно показывается `Себестоимость товарного P&L WB`,
рассчитанная по товарным строкам WB; эти два показателя нельзя подменять друг
другом.

Новые immutable report rows сохраняют источник примененной себестоимости:
`unit_cost`, `cost_method`, `cost_match_status`, `cost_source_kind`,
`cost_source_period_start`, `cost_source_period_end` и
`cost_source_document`. Допустимые основные статусы подбора:
`exact_week_exact_kind`, `nearest_week`, `cross_kind`, `missing`. Старый отчет
без этих полей остается читаемым, но web-кабинет не восстанавливает источник
предположениями и предлагает пересборку.

Read-only endpoint `GET /api/reports/{id}/cogs-reconciliation` использует
фильтры `period_start`, `period_end`, `wb_cabinet_id` и `client_company_id`.
Он разлагает `1С календарь − товарный P&L WB` на переходящие недели
комиссионера и выкупов, разницу совпадающих недель и корректировки закрытия
месяца. Сумма компонентов обязана равняться общей дельте с точностью до 1 ₽;
необъясненный остаток больше допуска получает `needs_review`. Строки
`nearest_week`, `cross_kind` и `missing` выводятся отдельной таблицей с ценой
единицы, периодом и документом-источником.

Основной расчет использует поле `Себестоимость`: в нем уже учтены распределенные
допрасходы 1С, поэтому `extra_costs_value` для этого источника заполняется
нулем и отдельно не прибавляется. `СебестоимостьБезНДС` остается только
сверочным вариантом через параметр `--sales-cost-amount-field` и получает метод
с `needs_review`.

## `sku_mapping`

Поля:

- `client_id`;
- `seller_account_id`;
- `organization_id`;
- `nm_id`;
- `vendor_code`;
- `barcode`;
- `onec_item_id`;

- `onec_characteristic`;

- `confidence`;

- `comment`;
- `updated_by`;
- `updated_at`.

Product-card discovery из WB Content дает входы для маппинга:

- `nmID` -> `nm_id`;
- `vendorCode` -> `vendor_code`;
- `sizes[].skus[]` -> кандидаты для `barcode`;
- `sizes[].techSize` и `sizes[].chrtID` -> размер и характеристика WB;
- `subjectName`, `brand`, `title` -> справочные поля для ручной проверки.

Внешний технический референс `Finmodel-2.0`: старый скрипт `katalog.py`
разворачивал каждую карточку WB в строки по `sizes[].skus[]` и хранил `org_id`,
`nmID`, `imtID`, `nmUUID`, `subjectID`, `subjectName`, `brand`, `vendorCode`,
`techSize`, `sku`, `chrtID`, `createdAt`, `updatedAt`. В текущем MVP переносится
только технический подход к плоскому mapping-candidate snapshot `*.flat.json`;
компании, данные и токены из референса не переносятся.
С 2026-07-08 источник правды для `sku_mapping` - собственный сервис
сопоставления из `docs/specs/marketplace-1c-mapping-service.md`.

Сервис хранит marketplace items, 1С items, candidates, текущую accepted-связь и
append-only журнал решений. Данные из 1С-модуля маркетплейсов, TXT/TSV/CSV
выгрузки и старые `sku_mapping` snapshots импортируются в сервис: однозначные
строки становятся подтвержденными current mappings, а skipped/conflict строки
остаются очередью ручной проверки. Сам файл не является самостоятельным
источником правды вне сервиса.

Первый расчетный `sku_mapping` строится на уровне товара маркетплейса:

- ключ WB: `seller_account_id + nm_id + vendor_code`;
- ключ Ozon: `seller_account_id + offer_id/product_id/sku`;
- ключ 1С: `onec_item_id`, с `onec_article` и характеристикой как справочными
  полями;
- автоматические кандидаты строятся по barcode, артикулу, offer id, SKU и
  названию, причем несколько методов на один товар 1С считаются одним
  кандидатом;
- импортированный из файла accepted mapping имеет приоритет над автоматическим
  кандидатом, а ручной accepted mapping имеет приоритет над импортом и авто;
- если сервиса еще нет в runtime, emergency fallback остается прежним:
  TXT/TSV/CSV mapping upload или `vendor_code` WB против `Артикул` 1С с явным
  статусом `needs_review`;
- если один `nm_id` имеет несколько `sizes[].skus[]`, создается одна строка
  маппинга на `nm_id + vendor_code`, без дробления по `sku`/баркоду;
- `barcode` и размерные поля WB остаются справочными/контрольными, но не
  являются основным ключом маппинга;
- если артикул 1С не найден, статус `missing`;
- если один артикул 1С ведет к нескольким номенклатурам, статус `ambiguous`.

# Calculation

Формула MVP:

```text
gross_profit =
  net_revenue
  - wb_commission
  - logistics
  - storage
  - acceptance
  - wb_promotion
  - penalties_and_holdbacks
  - acquiring
  - cogs_from_1c_with_extra_costs
```

`gross_profit` — внутреннее legacy-поле, которое в клиентском интерфейсе
называется `Управленческая прибыль WB`. Исторические уже сохраненные
legacy-отчеты могут показывать прежние
поля только для read-only совместимости:

```text
legacy_vat = net_revenue * 5 / 105
legacy_revenue_tax = net_revenue * 1%
profit_after_taxes = gross_profit - legacy_vat - legacy_revenue_tax
tax_method = "legacy: НДС внутри цены 5/105; налог с выручки 1%"
```

Новые расчеты эту формулу не применяют: при отсутствии явного профиля 1С или
действующего ручного исключения налоговый слой остается пустым и получает
`missing_tax_profile`.

Для профильного расчета по `tax_profile` организации 1С НДС сначала
раскладывается на исходящий, входящий и НДС к уплате:

```text
if vat_mode = included:
  vat_output = net_revenue * vat_rate / (100 + vat_rate)
  revenue_without_vat = net_revenue - vat_output
if vat_mode = excluded:
  vat_output = net_revenue * vat_rate / 100
  revenue_without_vat = net_revenue
if vat_mode = none:
  vat_output = 0
  revenue_without_vat = net_revenue

vat_input =
  product input VAT from confirmed 1C cost fields
  + WB service VAT calculated from service gross amount with VAT inside
  + fallback distributed 1C service VAT when WB allocation base is absent
vat_payable = vat_output - vat_input
```

Входящий НДС по WB-услугам считается не из факта уплаты налогов, а из
детализации WB-расходов: если закрывающий документ/1С показывает, что категория
является услугой с НДС, то строковая WB-сумма считается суммой с НДС внутри и
для 2026 года раскладывается по расчетной ставке `22/122`. Явные WB VAT-поля
(`vwNds`, `agencyVat` или аналоги) имеют приоритет, если WB начнет отдавать их
в детализации. 1С `СуммаНДС` по услугам/УПД используется как контрольная сумма:
она агрегируется по организации, неделе и категории услуги, а витрина показывает
`vatInputFromWb`, `vatInputFrom1c`, `vatInputDifference` и
`vatInputCompleteness`.

`vat_input` не складывает WB и 1С дважды: если есть WB-база для распределения,
в расчет принимается WB-расчет по SKU, а 1С остается сверкой. Если WB-базы для
категории нет, но в 1С есть `СуммаНДС`, эта часть распределяется fallback-базой
и получает статус неполной сверки.

Для НДС-сверки категории `Комиссия WB` и `Логистика` объединяются в один
контрольный блок `Комиссия WB + Логистика`, потому что в закрывающих
документах/1С эти суммы могут называться иначе, чем в товарной детализации WB.
В управленческом P&L расходы остаются раздельными: комиссия, логистика,
хранение, продвижение и прочие статьи не смешиваются.

Статусы: `confirmed` — расчетный WB НДС и 1С сходятся в пределах допуска,
`partial` — есть только один источник или распределение сделано по fallback-базе,
`missing` — входящий НДС и контрольный источник не найдены, `mismatch` — WB и 1С
расходятся выше допуска.

## Управленческое допущение по входящему НДС

Staff-only политика `input_vat_policy` задаётся на каноническую организацию 1С,
имеет режим, период действия, причину, автора и audit-событие. Режим
`accounting_fact` использует только фактически подтверждённые источники. Режим
`management_assumption` разрешает отдельный сценарий для юнит-экономики, но не
переименовывает его в бухгалтерский факт. Для недельной витрины период политики
проверяется по дате закрытия недели, поэтому неделя, закрывающаяся 01.03.2026,
входит в сценарий с этой даты.

Для организации «Галустов Рафаэль Рудольфович» сценарий действует с
2026-03-01 без конечной даты. Товарный входящий НДС считается на одном товаре,
документе и неделе как положительная разница `Себестоимость -
СебестоимостьБезНДС`, затем распределяется на объём WB. Отсутствующее поле,
нулевая база количества, отрицательная разница, неполный источник или
неразрешённое сопоставление не превращаются в ноль и сохраняют настоящий
blocker.

Расчётный НДС услуг WB равен `22/122` от комиссии, логистики, хранения,
приёмки, продвижения и эквайринга; штрафы исключены. Сценарные суммы не меняют
выручку, себестоимость без НДС или прибыль до налогов и влияют только на
`vat_input` и `vat_payable`. Источники не складываются дважды. Активные записи
книги покупок 1С имеют приоритет и отключают сценарий; при расхождении источников
остаётся `mismatch`.

Если обновлённые источники или новая группировка строк одновременно изменяют
P&L, управленческий сценарий материализуется как аудируемый VAT-only overlay на
строки текущего опубликованного отчёта. Overlay переносит сценарные суммы по
детерминированному ключу `неделя + nmId + артикул WB + схема`, уточняет статус
полноты по штрихкоду и до копейки сверяет входящий НДС. Выручка с НДС, выручка
без НДС, себестоимость без НДС, исходящий НДС и прибыль до налогов обязаны
совпасть с исходным отчётом; новый draft при этом получает lineage обновлённых
1С-источников и неизменяемого WB snapshot. Несовпадение grain или checksum
останавливает материализацию без частичной записи.

Read-only загрузка включает `Document_РасходыПриИмпорте` с товарными строками и
разделами, `AccumulationRegister_НДСПредъявленный_RecordType`,
`Document_ОтражениеНДСКВычету`,
`Document_ПодтверждениеОплатыНДСВБюджет` и книгу покупок. Банковский платёж не
является самостоятельной суммой вычета.

`management_assumption` не создаёт blocker `vat_input_unconfirmed`, но всегда
создаёт предупреждение и review-задачу `vat_input_management_assumption`. UI
показывает «Расчётный входящий НДС» и «Расчётный НДС к уплате» с явной пометкой,
что книга покупок 1С эти суммы не подтвердила.

Для ОСНО товарный P&L считается на базе без НДС:

```text
revenue_for_pnl = revenue_without_vat
cogs_for_pnl = 1C себестоимость без НДС
wb_service_expenses_for_pnl = WB service gross amount - deductible service VAT
profit_before_income_tax =
  revenue_for_pnl
  - cogs_for_pnl
  - wb_service_expenses_for_pnl
  - other_expenses_without_vat
profit_after_taxes = profit_before_income_tax
income_tax_included = false
tax_completeness = "vat_confirmed_ndfl_not_allocated"
pnl_vat_mode = "without_vat_for_osno"
```

Новая сверенная ревизия использует
`methodology_version = excel-mvp-q2-2026-v6-osno-reconciled`. Номер `v6`
продолжает уже существующую локальную ревизию `v5`; имя из первоначального
плана `v4-osno-reconciled` не переиспользуется, чтобы не создавать более новую
сборку с меньшим номером версии. Для каждой новой строки ОСНО
`pnl_vat_mode = without_vat_for_osno`, а `profit` и `profitBeforeTax` до НДФЛ
обязаны совпадать.

`vat_5_from_revenue` остается внутренним совместимым полем, но при профильном
ОСНО заполняется как `vat_payable`, а не как исходящий НДС. Если профильный
режим включен, но для организации 1С не найден `tax_profile` на период строки,
налоговые суммы не подставляются по чужой ставке, строка получает
`needs_review`, `tax_method = "Налоговый профиль не найден"` и источник
`missing`.

Для организаций на общей системе с НДС 22% и выручкой WB, считающейся ценой с
НДС внутри, используется профиль `tax_system = "ОСНО"`, `vat_rate = 22`,
`vat_mode = included`, `revenue_tax_rate = 0`,
`income_tax_kind = ip_ndfl_progressive`. НДС не является статьей управленческого
P&L: исходящий НДС, входящий НДС и `vat_payable` показываются отдельной сверкой,
но не уменьшают и не увеличивают `profitBeforeTax`/`profit`. Входящий НДС по
услугам WB считается из WB-сумм с НДС внутри и сверяется с 1С `СуммаНДС`. Если
для P&L без НДС не хватает подтвержденной базы разделения себестоимости или
услуг, строка получает `needs_review` и соответствующий `tax_completeness`.
Возвраты считаются теми же формулами со знаком минус.

НДФЛ ИП на ОСНО считается отдельно по организации и календарному году, по
накопленной базе и прогрессивной шкале. В v1 НДФЛ не распределяется по SKU без
подтвержденной годовой базы и правила распределения; товарная строка показывает
`income_tax_included = false`, `income_tax = 0` и не считается полной чистой
прибылью бизнеса.

Актуальные внешние источники для налоговых правил перед реализацией и
пересчетом: ФНС по НДС 22% и расчетной ставке 22/122
`https://www.nalog.gov.ru/rn25/news/activities_fts/16590316/`, ФНС по НДС при
УСН и вычетам `https://www.nalog.gov.ru/rn77/taxation/taxes/nds_usn/`,
каноническая промостраница ФНС по изменениям и прогрессивной шкале НДФЛ
`https://www.nalog.gov.ru/rn38/promo/new2025/`, ФНС по НДФЛ ИП и
профессиональным вычетам
`https://www.nalog.gov.ru/rn77/taxation/taxes/ndfl/ndfl_ip/`.

Если 1С/ОПиУ дает готовую контрольную сумму `НДС с продаж` или другого налога,
она используется для сверки и объяснения расхождений. Фактические налоговые
регистры 1С не распределяются по товарам.

СПП считается только из подтвержденного источника. В текущей версии источником
является поле `cashbackDiscountSum` из `WB sales-reports/list`; оно
распределяется на товарные строки по доле выручки WB после СПП внутри
недели/кабинета/типа отчета. Если недельный сводный отчет WB не загружен, в
Excel пишется `СПП не передается текущим источником`, а не ноль без пояснения.
Перед изменением формулы СПП/выручки нужно выбрать один свежий контрольный
`reportId` и собрать audit pack: `sum(detail.retailAmount)`,
`sum(detail.cashbackDiscount)`, `retailAmountSum`, `cashbackDiscountSum` и
`retailAmountSum - cashbackDiscountSum`. Этот audit pack хранит только
контрольные суммы и ссылки на локальные snapshots, без raw-строк WB.

`Выручка после СПП` — контрольная выручка внутри WB-методики, то есть текущая
`net_revenue` расчетной витрины. С общей выручкой 1С/ОПиУ ее нельзя сравнивать
напрямую, если в ОПиУ есть продажи не только Wildberries. В листе
`Сверка с 1С ОПиУ` общая выручка и общая себестоимость ОПиУ не выводятся как
товарный контроль; помесячная сверка с 1С строится по одинаковой выборке
РВБ-документов, количеству, себестоимости и расходам маркетплейса. `Выручка до
СПП` считается как `Выручка после СПП + СПП`.

Главный товарный показатель прибыли не называется чистой прибылью бизнеса.
Клиентское название для профильного расчета ОСНО: `Управленческая прибыль WB`.
Для старых legacy-отчетов внутреннее поле `profit_after_taxes` остается
совместимым, но клиентские подписи больше не должны обещать, что НДС включен в
P&L как налоговый расход.

Денежные значения считаются decimal-логикой. В Excel денежные значения
отображаются с двумя знаками.

Для `Хранение` и `WB Продвижение` контрольной суммой является недельный
финансовый отчет WB:

- `paidStorageSum` задает итог хранения за неделю;
- `deductionSum` задает итог `WB Продвижение` за неделю;
- если загружены отдельные paid storage / promotion stats API, их суммы по
  `nmId` используются как товарная база распределения;
- если отдельные API не загружены или не дали товарной базы, используется
  товарная детализация из WB Finance;
- товарная детализация используется как ключ распределения по `nmId`/артикулу,
  но не как финальная сумма периода;
- если сумма товарной детализации отличается от недельного финансового отчета,
  товарные доли масштабируются коэффициентом
  `сумма_фин_отчета_WB / сумма_API_детализации`;
- после округления до копеек остаток распределяется по строкам с наибольшей
  дробной разницей, чтобы сумма товарных строк ровно сходилась с недельным
  финансовым отчетом WB;
- если API-детализация по статье за неделю нулевая, но недельный отчет WB
  содержит сумму, используется запасной ключ по выручке WB, а строка получает
  статус `Нет базы API, распределено по выручке, нужна проверка`;
- если нет ни API-базы, ни выручки, сумма распределяется поровну между
  строками периода со статусом `Нет базы API и выручки, распределено поровну,
  нужна проверка`.
- если `Хранение` или `WB Продвижение` пришли из WB отдельной строкой без
  реального товара (`nmId` пустой или равен `0`, нет артикула и штрихкода), эта
  строка не считается товаром: сумма распределяется на товарные строки той же
  недели/кабинета по товарной детализации, а если ее нет — по выручке WB; строка
  без товара остается только в аудите распределения и ошибках данных, но не
  выводится на клиентский лист `Юнит экономика` как отдельный товар.

1С УПД используется для бухгалтерской сверки общей суммы и категорий, но не
заменяет недельный WB Finance report как экономический период распределения.

Статусы качества:

- `reliable`;
- `missing_cost`;
- `missing_mapping`;
- `ambiguous_mapping`;
- `partial_source`;
- `expense_without_sku`;
- `account_org_mismatch`;
- `excluded`;
- `tax_profile_missing`;
- `tax_review`;
- `needs_review`.

Строки со статусом, отличным от `reliable`, должны быть видны в `Ошибки данных`.
В Excel статусы качества и комментарии маппинга выводятся на русском языке,
например `Неполный источник`, `Нет себестоимости 1С`,
`Неоднозначное сопоставление`, `Себестоимость 1С требует сверки`,
`Налоговый профиль не подтвержден`, `Налоговый расчет требует сверки`.
Налоговая проблема не должна переводиться или учитываться как проблема
себестоимости только потому, что оба статуса требуют ручной проверки.
Если строка одновременно находится в неполной WB-загрузке и имеет более
прикладную проблему маппинга или себестоимости, в строковом статусе показывается
прикладная проблема; общий факт неполной загрузки сохраняется в README/source
notes и строках без других проблем.

Отсутствие себестоимости блокирует строку только при ненулевом чистом товарном
количестве. Если продажи и возвраты одного товара внутри расчетной строки
полностью взаимно закрылись и `net quantity = 0`, COGS также равен нулю и
отсутствующий cost snapshot не должен создавать ложный `missing_cost`.

В web-кабинете предупреждение `cogs_reconciliation_failed` открывает только
строки с проблемой себестоимости, а не общий список всех строк со статусом не
`ОК`. Код сохраняется для обратной совместимости API, но причина возвращается в
`reviewReasons`, а не в `blockingReasons`. Приближенная или отсутствующая
себестоимость не блокирует формирование, скачивание или публикацию Excel:
ограничение остается видимым в статусах строк, расшифровке и листе ошибок.
Расшифровка обязана раздельно показывать:

- строки `Себестоимость 1С требует сверки`, где в расчет уже подставлена
  ближайшая доступная себестоимость и после загрузки точного недельного слоя
  требуется пересборка;
- строки `Нет себестоимости 1С`, где действующий стоимостной слой не найден и
  его нужно исправить в 1С до обновления источников и пересборки.

Для выбранных фильтров `/api/reports/{id}/rows?preset=missingCost` возвращает
аддитивный `costIssueBreakdown` с общим количеством, количеством строк для
сверки и количеством строк без себестоимости. Формат `items` и URL API не
меняются. Окно расшифровки показывает причину статуса, использованную сумму
себестоимости и конкретное следующее действие. Предупреждение можно отметить как
просмотренное, но это не меняет расчетный статус строк. Само предупреждение
исчезает только после обновления данных 1С и пересборки immutable report run.

DB-first экспорт обязан создавать этот же полный набор листов в указанном
порядке из одного сохраненного report run. Нельзя заменять его компактным
workbook с частью витрин. `Дашборд` является активным листом, а при неполном
покрытии остатков лист `Упущенные продажи` явно показывает причину
`Не рассчитано: история остатков покрывает X из Y дней`.

Опциональный лист:

- `ИИ-резюме`.

`README` должен показывать клиента, две организации, два кабинета, период, статус
периода, дату расчета, версию методики, ограничения и то, что реклама исключена
из MVP.

Лист `Дашборд` является первым видимым листом и показывает период, статус
периода, дату расчета, KPI, статусы данных, месячную динамику, динамику
`Управленческой прибыли WB` по неделям, топ прибыльных товаров и топ
убыточных товаров. KPI должны включать выручку до СПП, СПП, `% СПП`, выручку
после СПП, продажи, возвраты, чистое количество, долю возвратов,
прибыльные/убыточные SKU и долю строк со статусом `ОК`. Месячная динамика
показывает месяцы выбранного `report_period`, явно помечает неполные месяцы и
показывает изменение месяц к месяцу по выручке после СПП, маржинальному доходу
WB и WB-расходам.
Топ прибыльных товаров показывает строки с положительной себестоимостью 1С,
положительным маржинальным доходом на штуку и без блокирующих ошибок маппинга
или отсутствующей себестоимости. Строки со статусами `ОК`, `Себестоимость 1С
требует сверки` и `Тип отчета WB определен эвристикой` могут попадать в топ,
при этом статус данных выводится отдельной колонкой. Товары с нулевой или
отрицательной себестоимостью остаются в детализации и диагностике, но не
попадают в топ прибыльных товаров.

Лист `Юнит экономика` является главным клиентским листом и группирует расчет по
неделе, организации 1С, кабинету WB и товару. Видимые клиентские колонки
разделяют идентификаторы разных источников: `Номер отчета WB`,
`Дата отчета WB`, `Документ-отчет`, `nmId WB`, `Артикул WB`,
`Артикул 1С`, `Баркод`, товар, схема продажи, продажи в штуках, возвраты в
штуках, чистое количество, процент возвратов, выручка до СПП, СПП, `% СПП`,
выручка после СПП, НДС, выручка без НДС, себестоимость 1С, комиссия WB,
логистика WB, хранение WB, приемка WB, продвижение WB, штрафы/доплаты WB,
эквайринг WB, `НДС к уплате`, `Управленческую прибыль WB`, `прибыль до НДФЛ`,
маржу до НДФЛ, прибыль до НДФЛ на штуку,
русский статус данных, причину статуса, статус СПП, налоговый режим/ставку и
источник налогового профиля.

Лист `Ликвидность МД` является клиентской управленческой витриной ликвидности
ассортимента. Он строится не из ручной Excel-модели, а из существующих строк
`Юнит экономика`, сгруппированных по месяцу, организации 1С, кабинету WB,
товару, артикулам WB/1С, баркоду и схеме продажи. Статус ликвидности считается
на месячном агрегате, чтобы один товар в одном месяце не получал разные
недельные статусы. Основной итог и сортировка — `Прибыль до НДФЛ`; каскад
МД1-МД6 выводится как диагностика причины:

```text
МД1 = Выручка после СПП - Себестоимость 1С
МД2 = МД1 - Комиссия WB
МД3 = МД2 - Хранение WB
МД4 = МД3 - Логистика WB - Приемка WB
МД5 = МД4 - Продвижение WB
Управленческая прибыль WB = МД5 - Штрафы/доплаты WB - Эквайринг WB
Прибыль до НДФЛ = Управленческая прибыль WB - подтвержденный профильный налог
  на доход, кроме НДФЛ предпринимателя
```

`Приемка WB` входит в МД4, чтобы каскад не расходился с принятой формулой
прибыли. Для итоговых колонок `Управленческая прибыль WB` и `Прибыль до НДФЛ`
витрина суммирует принятые строковые значения из `Юнит экономика`, если они
доступны;
это защищает месячную группировку от копеечного дрейфа округлений и сохраняет
сверку с исходной витриной. Статусы ликвидности: `Только затраты - нет продаж`, `Нулевая
маржинальность`, прибыльные группы `до 500`, `500-1000`, `1000-30000` и
`более 30000 руб. в месяц`, а также убыточные статусы по первой отрицательной
ступени каскада, включая `Убыточный: налоги`. Если агрегат содержит
неблокирующий или блокирующий статус качества данных, витрина показывает
`Нужна проверка данных`, а рядом выводит исходные `Статус данных` и
`Причина статуса`; такие строки нельзя трактовать как надежные управленческие
решения без проверки источников.

В блоке `Топ убыточных товаров` на дашборде строки сортируются по
`прибыли до НДФЛ` по возрастанию, затем по прибыли до НДФЛ на штуку,
затем по доле возвратов по убыванию. Блок показывает товар, артикулы, чистое
количество, возвраты, процент возвратов, выручку после СПП, маржинальный доход,
доход на штуку, класс убытка, главную причину убытка и статус данных.

Лист `Сверка с 1С ОПиУ` является клиентским контрольным листом. Основная
помесячная сверка показывает `WB количество`, `1С количество`, дельту
количества, `Себестоимость 1С в WB-расчете`,
`Себестоимость по валовой прибыли 1С`, дельту себестоимости, расходы МП по
WB-расчету и расходы МП по ОПиУ. WB-себестоимость берется из строк
`Товары по отчетам 1С`, то есть группируется по фактической дате сматченного
документа 1С, а не по месяцу недели WB. Если документ 1С еще не найден, для
диагностики используется ожидаемая дата документа. Контрольная себестоимость 1С
берется из сматченных документных строк листа `Валовая прибыль 1С` по той же
выборке РВБ-документов и также группируется по фактической дате документа 1С.
Общая выручка и общая себестоимость ОПиУ не участвуют в товарной сверке. ОПиУ
остается справочным управленческим блоком для расходов РВБ:
`Расходы РВБ общий блок` и расшифровка РВБ по статьям показываются ниже и не
подменяют сверку товарной себестоимости.

Главная причина убыточности считается детерминированно по крупнейшему фактору
среди себестоимости, комиссии, логистики, хранения, продвижения, штрафов/
удержаний, эквайринга, налогов и возвратов. Если статус данных не `ОК`, причина
убыточности выводится как `Нужна проверка данных`.

Класс убытка группирует главную причину для управленческого действия:
`Высокая закупка / недостаточная наценка`, `Возвраты + логистика`,
`Прочие расходы` или `Нужна проверка данных`.

Для клиентского UX применяются правила условного форматирования: отрицательная
прибыль и отсутствующие данные выделяются красным, строки со сверкой и высокими
долями хранения/продвижения — желтым, хорошая маржинальность — зеленым.

Технические идентификаторы сохраняются в скрытых листах и snapshots для
воспроизводимости, сверки и аудита, но не должны мешать клиенту в основном
отчете.

Лист `Сверка по отчетам WB` группирует расчетную витрину по неделе,
`wb_report_id`, кабинету WB и организации 1С. В колонках выводятся продажи,
возвраты, итоговое количество, выручка, комиссии, логистика, хранение, приемка,
`WB Продвижение`, удержания/штрафы/доплаты, эквайринг, себестоимость 1С,
`НДС к уплате`, профильный налог на доход, `Управленческая прибыль WB`,
`прибыль до НДФЛ`, маржа до НДФЛ, статус
данных и количество строк витрины. Этот лист нужен для ручной сверки с
финмоделью/fact-таблицей по номеру отчета WB.

Лист `Сводный отчет WB` показывает недельный report-table из
`sales-reports/list` без товарной детализации: номер отчета WB, тип отчета,
период, выручку WB, сумму к перечислению, логистику, хранение, приемку,
`WB Продвижение / удержания`, штрафы, доплаты, cashback и банковский платеж.

Лист `WB поля отчета` является компактным диагностическим блоком по тем же
строкам `sales-reports/list`. Он выводит `reportId`, `reportType`,
`retailAmountSum`, `cashbackDiscountSum`, `forPaySum`, `bankPaymentSum`,
`paidStorageSum`, `deductionSum`, `penaltySum` и `additionalPaymentSum`.
`forPaySum` и `bankPaymentSum` не считаются подтвержденным источником выплаты
1С; статус выплаты остается `Нужен источник выплаты 1С` до согласования
отдельного read-only источника выплаты.

Лист `Сверка с 1С` группирует строки так, как их удобно сверять с документами
1С:

- ожидаемая дата `Отчета комиссионера` считается как воскресенье закрываемой
  недели, а `Уведомления о выкупе` — как следующий понедельник; фактическая
  дата документа 1С всегда имеет приоритет над ожидаемой;
- период продаж — понедельник-воскресенье предыдущей недели;
- `reportType=1` из `sales-reports/list` является основным признаком типа
  `Отчет комиссионера`;
- `reportType=2` из `sales-reports/list` является основным признаком типа
  `Уведомление о выкупе`;
- суффиксный fallback по `reportId` используется только когда `reportType` не
  доступен, и такая строка получает статус `report_type_fallback`;
- в колонке `WB reportId в пакете` перечисляются исходные технические номера WB,
  которые вошли в пакет.

Первичные WB Documents используются как бухгалтерское доказательство.
Read-only загрузка `wb_redeem_notifications` ограничивается выбранным периодом
и категорией `Уведомление о выкупе`; исходный подписанный ZIP сохраняется только
в локальном source snapshot. В DB сохраняются metadata, hash, reportId,
количество и итоговые суммы первичного XLSX, но не товарные строки и не подпись.
Excel, Markdown и docs не содержат исходный архив или клиентские товарные
данные. Старые отчеты без этого source type остаются совместимыми и получают
`Не проверено`, пока не создан новый immutable run.

Для сверки с печатной формой еженедельного отчета WB лист дополнительно
показывает контрольные поля из `sales-reports/list` по тому же кабинету, неделе
и типу документа:

- `PDF 1. Стоимость реализовано` = `retailAmountSum`;
- `PDF 1.1 Товар реализован` = `retailAmountSum - cashbackDiscountSum`;
- `PDF 1.4 Компенсация скидки` = `cashbackDiscountSum`;
- `PDF 8. К перечислению` = `bankPaymentSum`;
- `Контроль удержаний WB (1 - банк)` = `retailAmountSum - bankPaymentSum`.

Эти поля являются контрольной сверкой печатной формы WB, а не новой базой
управленческой прибыли. Дельты рядом с ними показывают, сходится ли
детализация MVP с недельным сводом WB по выручке, логистике, хранению,
`WB Продвижению` и штрафам/доплатам.

Лист `Сверка документов 1С` является отдельным контролем корректности загрузки
документов в 1С. Он сопоставляет ожидаемые WB-пакеты с фактическими документами
из `AccumulationRegister_Продажи`:

- `Отчет комиссионера` сверяется с документом 1С `ОтчетКомиссионера` по той же
  неделе продаж; сумма документа сверяется по недельной контрольной строке WB
  `retailAmountSum` из `sales-reports/list` `reportType=1`, а не по сумме
  детальных товарных строк;
- `Уведомление о выкупе` сверяется с документом 1С `РасходнаяНакладная` по
  неделе даты самой расходной накладной; контрольное количество для 1С берется
  как `WB продажи` только из детализации `reportType=2`, потому что расходная
  накладная отражает положительное движение выкупа. Строки основного отчета
  `reportType=1` не могут входить в количество или сумму выкупного пакета даже
  при совпадении недели, товара и кабинета. `WB возвраты` по выкупному отчету
  выводятся отдельной
  справочной колонкой и не уменьшают расходную накладную, пока в 1С не
  подтвержден отдельный возвратный документ;
- тип пакета детальной строки определяется прежде всего по исходному полю WB
  `reportType`; эвристика по номеру отчета разрешена только для старых snapshots,
  где это поле действительно отсутствует, и помечается как fallback качества;
- для каждого пакета выводятся ожидаемые и фактические продажи, возвраты и
  чистое количество, ожидаемая и фактическая сумма документа, `WB к
  перечислению (forPaySum)`, справочный `1С оборот взаиморасчетов`, документы
  1С, статус сверки документа и отдельный статус выплаты.
- если у `Отчет комиссионера` сумма совпала с `retailAmountSum`, но количество
  отличается, статус должен быть мягким `Проверить товарные строки`, чтобы не
  смешивать финансовую сверку документа с разбором номенклатурной детализации.
- для каждой недели отдельно показываются `WB отчет продаж` из `reportType=1`
  и `WB отчет выкупов` из `reportType=2`; для строки `Уведомление о выкупе`
  дополнительно выводятся `retailAmountSum`, `forPaySum`, `bankPaymentSum`
  выкупного отчета, сумма `РасходнаяНакладная` 1С и дельты к этой накладной.
  Эти дельты являются диагностическими: бумажное уведомление о выкупе,
  загруженное в 1С, может быть суммой нетто после удержаний и не обязано
  совпадать с API-полями `retailAmountSum`, `forPaySum` или `bankPaymentSum`.
  Аналогично, дельта возвратов для `Уведомление о выкупе` не является жесткой
  ошибкой загрузки 1С, если `WB продажи` совпали с расходной накладной.

Этот лист нужен для диагностики случаев, когда документ WB мог быть загружен в
1С неправильной суммой, количеством, датой или типом документа. Для выкупных
документов сумма расходной накладной остается справочной сверкой регистра
продаж. Денежный показатель `WB к перечислению (forPaySum)` выводится отдельно
и не делает строку ошибочной, пока в 1С не подтвержден read-only источник именно
выплаты продавцу.

DB-first mart `documentReconciliation` использует тот же matcher ожидаемых
WB-пакетов и фактических `OnecGrossProfitDocumentRow`, что и Excel-лист. Нельзя
создавать все строки с пустым `onecDocuments`, если документы 1С уже загружены.
Информационный `payoutStatus` сам по себе не является readiness issue, пока нет
принятого read-only источника фактической выплаты; блокируют отсутствие
документа, несовпадение обязательных количеств/сумм и отдельный неполный период.

Web-сверка продаж WB ↔ 1С использует единый учетный период по фактической дате
сопоставленного документа 1С. Поэтому продажи недели 27.04–03.05 относятся к
апрелю, если отчет комиссионера проведен 30 апреля. Период самой недели WB
показывается отдельно. Для `Отчета комиссионера` сопоставляются чистое количество и выручка с
НДС; обе величины должны совпадать с 1С в пределах принятого допуска. Для
`Уведомления о выкупе` с `РасходнойНакладной` сопоставляется только положительное
количество продаж. Розничная сумма WB и сумма расходной накладной 1С нетто после
удержаний показываются рядом справочно, но не вычитаются друг из друга, не входят
в дельту выручки и не создают статус расхождения. Возвраты выкупов также
показываются отдельно и не уменьшают расходную накладную без подтвержденного
возвратного документа 1С.

На `Обзоре` главная карточка выручки показывает выручку товарной юнит-экономики
WB в базе применённого налогового профиля. В той же карточке вторичной строкой
показывается календарная `Выручка 1С с НДС`: сумма поля `Сумма` проведённых
документов 1С за выбранный календарный период, соответствующая экрану 1С
`Валовая прибыль по номенклатуре` при тех же датах и организации. В неё входят
`ОтчетКомиссионера`, `РасходнаяНакладная` по выкупу и отдельные корректировки
1С; дата отбора — дата проведения документа в 1С. Разные базы подписываются и
не складываются. Если подтвержденных документов 1С нет, вторичная строка
показывает явное отсутствие данных, а не ноль и не подменяется данными WB.
Подробная календарная сверка остаётся во вкладке `Проверки`.

В той же витрине показатель `Выручка WB по документам, с НДС` всегда имеет
явную формулу `Выручка комиссионера WB + Розница выкупов WB`, где обе части
берутся из `retailAmountSum` соответствующих недельных документов WB
`reportType=1` и `reportType=2`. Отдельная карточка `Сверка комиссионера WB ↔
1С` показывает `1С − WB` по одним и тем же неделям продаж и должна быть нулевой
в пределах допуска.

Выкупы выводятся контрольной строкой `Первичка WB ↔ Накладная 1С`. Пока
первичное уведомление WB не загружено, строка показывает
`Юнит-экономика рассчитана; документальная сверка выкупов не завершена`, а рядом
справочно выводится `Накладная 1С − Розница WB` как разница ценовых баз без
статуса ошибки. Нулевой результат нельзя получать подстановкой суммы 1С на обе
стороны. Тем самым витрина разделяет сопоставимую документную сверку и
аналитическое сравнение розничной и выкупной цены.
`Выручка WB по товарным строкам, с НДС` и `Выручка WB без НДС` остаются базой
товарного P&L WB и подписываются отдельно от документной сверки.

В блоке `Показатели` рядом с выручкой выводится карточка `Себестоимость продаж
1С`. Она равна прямой сумме `Себестоимость` проведенных движений регистра 1С по
календарной дате и включает отчеты комиссионера, расходные накладные по выкупам
и корректировки закрытия месяца. Количество продаж 1С считается на той же базе:
чистое количество `ОтчетКомиссионера`, положительное количество
`РасходнаяНакладная` и отдельные количественные корректировки 1С.

Самостоятельная карточка `Себестоимость товарного P&L WB` равна сумме
`cogs_from_1c_with_extra_costs` по товарным строкам и фильтру недель продаж WB.
Для ОСНО используется P&L-база без входного НДС, для остальных режимов —
примененная подтвержденная база 1С. Карточка не скрывается при наличии строк
`Себестоимость 1С требует сверки`: сумма остается видимой, а количество таких
строк показывается предупреждением и ведет в расшифровку.

Web-кабинет визуально разделяет `Юнит-экономика WB` и `Контроль 1С`. Обе
карточки себестоимости открывают одну расшифровку. Формула прибыли подписывается
по примененному `pnl_vat_mode`: legacy/УСН использует валовую выручку с НДС и
отдельный налоговый мост, ОСНО — сопоставимую P&L-базу без НДС.

Для бухгалтерской сверки доступен отдельный показатель `Единый стандарт WB ↔
1С`. Он использует календарную дату проведения документа 1С, сумму
`retailAmountSum` WB для `Отчета комиссионера` и поле `Сумма выкупа` из
первичного файла WB `Уведомление о выкупе` для сопоставления с проведенной
`РасходнойНакладной` 1С. Подставлять сумму накладной 1С одновременно на обе
стороны сверки запрещено: это создает ложную нулевую дельту. Розница WB,
`forPaySum` и `bankPaymentSum` остаются отдельными несопоставимыми справочными
базами и не заменяют сумму первичного уведомления.

Правило применяется одинаково ко всем клиентам и кабинетам WB, без клиентских
исключений. Если immutable source snapshot не содержит первичного уведомления
или токен кабинета не имеет read-only доступа к категории WB `Документы`,
денежная сверка выкупа получает статус `Не проверено: нет первички WB`.
Отсутствие первички нельзя превращать в расхождение между розницей WB и 1С и
нельзя автоматически считать нулевой дельтой. Отдельные уведомления об обратной
реализации/возвратные документы 1С показываются как корректировки того же
выкупа, но не изменяют сумму исходной расходной накладной.

В web-кабинете карточка `Выкупы: первичка WB ↔ 1С` открывает read-only
расшифровку по выбранному периоду и кабинету. Для каждого выкупа показываются
период, номера документов WB и 1С, `Сумма выкупа` первичного уведомления,
сумма расходной накладной 1С, их сопоставимая дельта, розница WB справочно,
статус количества, возвратные корректировки и следующее действие. Пока
первичное уведомление не сохранено в source snapshot, карточка и строка
показывают `Не проверено`, а разница `1С − розница WB` подписывается только как
`Разница ценовых баз` и не получает статус ошибки. Строки без накладной 1С,
без первички WB или с несовпадением количества идут первыми. Расшифровка не
меняет исходные суммы или документы.

Каждая карточка KPI в web-кабинете получает текст формулы, базы и периода в
`data-tooltip`; подсказка открывается при наведении и при фокусе с клавиатуры.
В P&L WB-выручка всегда имеет префикс `WB`, чтобы не выглядеть дублем главной
карточки 1С.

Одновременно web-кабинет показывает самостоятельный итог `Выручка 1С за
календарный период`, равный отчету 1С `Валовая прибыль по номенклатуре` при тех
же датах и организации. В него обязательно входят оба типа проведенных
документов 1С: `ОтчетКомиссионера` и `РасходнаяНакладная` по выкупу. Например,
документ комиссионера, проведенный 30 апреля за WB-неделю 27.04–03.05, входит в
апрельский итог 1С, но остается майской строкой WB-периода. Этот календарный
итог не выдается за прямую дельту к розничной выручке WB: в разрезе выкупов
1С отражает договорную сумму выкупа из первичного уведомления, а
`retailAmountSum` WB — отдельную розничную базу.

Текущий регистр `AccumulationRegister_Продажи` содержит `Сумма`, `СуммаНДС` и
`Себестоимость`, но не является источником взаиморасчетов. Для справочной
колонки `1С оборот взаиморасчетов` используются read-only регистры
`AccumulationRegister_РасчетыСПокупателями` и
`AccumulationRegister_РасчетыСПоставщиками`, сгруппированные по организации,
контрагенту, документу и типу документа. Этот оборот не считается
подтвержденным аналогом `WB к перечислению (forPaySum)`, поэтому статус выплаты
остается `Нужен источник выплаты 1С`, пока не согласован отдельный 1С-источник
чистой выплаты.

Для точного сопоставления с 1С лист использует заголовки документов:
`Document_ОтчетКомиссионера.НомерВходящегоДокумента` нормализуется как
внешний `WB reportId`, а для `Document_РасходнаяНакладная` номер уведомления о
выкупе извлекается из комментария/основания печати. Если эти заголовки
доступны в read-only export, документ 1С сопоставляется с WB-пакетом сначала по
`reportId`; недельное сопоставление остается только fallback для старых
выгрузок без заголовков документов. Сумма заголовка документа не подставляется
в колонку `1С оборот взаиморасчетов`: этот справочный контроль заполняется
только из регистров `РасчетыСПокупателями` и `РасчетыСПоставщиками`, потому что
в 1С сумма документа, оборот взаиморасчетов и чистая выплата могут отличаться.
Отрицательные `ПриходнаяНакладная` без WB-пакета выводятся отдельным статусом
`Корректировка 1С`, а не как обычный лишний документ.

Лист `Товары по отчетам 1С` повторяет ту же 1С-пакетизацию, но на уровне товара:
`nmId`, артикул, баркод, номенклатура 1С, модель продаж, количества, реализация,
возвраты, расходы WB, себестоимость, валовая прибыль 1С, `Управленческая прибыль
WB`, `НДС к уплате`, профильный налог, `прибыль до НДФЛ`, маржа до НДФЛ и
статус данных.

В листе `Сверка с 1С` валовая прибыль 1С считается как
`Выручка нетто - Себестоимость 1С`. Это отдельный показатель от управленческой
юнит-экономики, где дополнительно вычитаются комиссия, логистика, хранение,
приемка, удержания и эквайринг WB.

Для полной сверки с отчетом `Валовая прибыль по номенклатуре` локальный
`sales_register.raw.json` должен содержать все движения 1С за период, включая
`ОтчетКомиссионера` и `РасходнаяНакладная` по выкупам WB. Если расходная
накладная не попала в snapshot, WB-строки выкупа остаются в WB-пакете, но их
нельзя считать сверенными с 1С.

Лист `Валовая прибыль 1С` строится напрямую из `AccumulationRegister_Продажи` и
группирует фактические документы 1С по неделе, организации, контрагенту и
регистратору. Он нужен для сверки с экраном 1С `Валовая прибыль по
номенклатуре`: в нем отдельно видны `ОтчетКомиссионера`, `РасходнаяНакладная`,
количество, `Сумма`, `СуммаНДС`, `Себестоимость` и валовая прибыль 1С. Этот
лист не заменяет управленческую юнит-экономику WB, потому что не вычитает
комиссии, логистику, хранение, приемку, удержания и эквайринг WB.

Лист `Сверка услуг WB` сравнивает УПД/поступления услуг 1С от маркетплейса с
WB-детализацией и недельным сводом WB по статьям: комиссия, логистика, хранение,
приемка, `WB Продвижение`, штрафы/доплаты и эквайринг. Для текущей методики
`WB Продвижение` должно сходиться с 1С-строкой `Оказание услуг «WB Продвижение»`
и с WB `deductionSum`; отдельные рекламные API в MVP не включены.

Нормализованный источник услуг 1С выбирается без клиентских исключений. Сначала
используются проведенные `Document_ПоступлениеТоваровУслуг` и строки
`Document_ПоступлениеТоваровУслуг_Услуги`. Если этот объект не опубликован в
OData или не дал подтвержденных строк WB, используется
`Document_ПриходнаяНакладная.Расходы`. Два источника не суммируются. В fallback
входят только документы, чья пара организация–контрагент подтверждена
движениями WB в `AccumulationRegister_Продажи`; обычные закупки и документы
других маркетплейсов исключаются. Отсутствующий или неоднозначный источник
остается `null`, а не подменяется нулем.

Web-кабинет разделяет расходную базу товарного P&L и документную сверку. Карточка
`Расходы WB в товарном P&L` использует базу, примененную налоговым профилем.
Карточки `Услуги WB по документам 1С` и `Сверка расходов WB ↔ 1С` сравнивают
сопоставимые суммы с НДС; в расшифровке отдельно показываются сумма без НДС,
НДС и итог. Подтвержденный статус требует расхождения не более 1 рубля в каждой
контрольной группе: `WB Продвижение`, `Штрафы/доплаты` и объединенные
`Комиссия + Логистика + Хранение + Приемка + Эквайринг + Прочие услуги WB`.
Взаимная компенсация расхождений разных групп не дает статус `Сверено`.
Отсутствие услуг 1С не блокирует рассчитанную юнит-экономику WB, но сохраняет
явный статус незавершенной бухгалтерской сверки.

В верхней части листа `Сверка услуг WB` выводится контрольный блок:

- `WB Продвижение`;
- `Штрафы/доплаты`;
- `Комиссия + Логистика + Хранение + Эквайринг`.

Последний блок сверяется суммарно, потому что в 1С часть услуг WB может быть
отнесена в строку комиссионного вознаграждения, а не в ту же категорию, что в
WB Finance API. Большой разрыв по одной категории, например логистике, не должен
трактоваться как незагруженная логистика без проверки этого суммарного блока.

Лист `Расшифровка услуг 1С` показывает строки УПД/поступлений услуг 1С:
неделю, организацию, контрагента, дату и номер УПД, входящий номер, комментарий
документа, услугу, сумму, НДС, итог и категорию сверки. Лист нужен, чтобы
пользователь мог проверить, из каких документов собраны суммы на листе
`Сверка услуг WB`.

Лист `Распределение расходов` показывает аудит распределения `Хранение` и
`WB Продвижение` по товарам: неделю, тип отчета, недельный `reportId` WB,
кабинет, организацию, статью, `nmId`, артикул, номенклатуру 1С, базу API по
товару, сумму API по неделе, контрольную сумму недельного финансового отчета
WB, коэффициент приведения, распределенную сумму, метод и русский статус
качества распределения. Этот лист подтверждает, что сумма товарных строк
совпадает с недельным финансовым отчетом WB даже при несовпадении периодов API
хранения/рекламы и даты УПД.

Основные листы с расчетами, маппингом, себестоимостью и ошибками оформляются как
Excel Table с включенными фильтрами, чтобы клиент мог быстро отбирать строки по
периоду начала/окончания, месяцу, кабинету, организации, товару, статусу и
суммам.

Лист `Расходы WB` является клиентским листом структуры расходов. В верхнем
блоке он показывает сумму каждой статьи, процент от выручки после СПП, значения
по месяцам и изменение месяц к месяцу. В детализации по строкам выводится общая
сумма WB-расходов и ее доля от выручки строки.

Лист `Возвраты` является клиентским листом аналитики возвратов. Он показывает
неделю, организацию 1С, кабинет WB, товар, `nmId WB`, артикул WB, артикул 1С,
баркод, продажи, возвраты, процент возвратов, сумму возвратов, маржинальный
доход WB после налогов, маржинальный доход на штуку, статус данных, главную
причину и причину возврата. В текущем MVP причины возвратов не подключаются из
отдельного источника; если причина не передается текущими snapshots, в строке
выводится `Причина возврата не передается текущими источниками`.

Лист `Упущенные продажи` является клиентским листом предварительной оценки
out-of-stock. Он показывает кабинет WB, товар, `nmId WB`, артикул WB, артикул
1С, баркод, дни в периоде, дни без остатка WB, дни критического остатка,
остаток 1С на складах, склады 1С с остатком, продажи, среднедневные продажи в
дни наличия, потенциально упущенные штуки, потенциально упущенную выручку,
потенциально упущенную прибыль, прибыль на продажу, управленческий вывод и
статус источника. Расчет упущенных штук, выручки и прибыли основан на
`STOCK_HISTORY_DAILY_CSV`; 1С остатки по складам выводятся как клиентский
контур пополнения и влияют на управленческий вывод, но не заменяют историю
наличия на складах WB.

По умолчанию пользователь видит только клиентские вкладки:

- `Дашборд`;
- `Юнит экономика`;
- `Ликвидность МД`;
- `Динамика`;
- `Расходы WB`;
- `Возвраты`;
- `Упущенные продажи`;
- `Сверка документов 1С`;
- `Сверка с 1С ОПиУ`;
- `Ошибки данных`;
- `Методика`.

Остальные листы остаются в workbook скрытыми как технические и сверочные:
сводки по кабинетам/организациям, исходные расходы WB, маппинг, себестоимость,
месячные сверки с 1С, расшифровка услуг и аудит распределения. Их можно
раскрыть при проверке методики, но они не должны быть основным UX. Лист
`Сверка документов 1С` остается видимым, потому что используется для ручного
контроля загрузки `Отчетов комиссионера`, `Уведомлений о выкупе` и
взаиморасчетов.

В видимых колонках Excel кабинет WB и организация 1С отображаются понятными
названиями. Технические идентификаторы `WB_ACCOUNT_1`, `WB_ACCOUNT_2` и ключи
организаций 1С сохраняются во внутренних snapshots и расчетных ключах для
воспроизводимости загрузки, но не должны попадать в основные клиентские колонки.

# Acceptance Criteria

MVP принят, если:

- строится клиентский отчет за выбранный `report_period`, заданный параметрами
  генератора или `report_run`;
- `source_coverage` WB/1С явно сохраняется и показывается в отчете; если
  coverage не закрывает выбранный `report_period`, отчет получает
  `partial_period`, `partial_source` или `needs_review`;
- строки вне выбранного `report_period` не попадают в клиентскую витрину; март
  исключается только для отчетов, где `report_period` начинается с апреля;
- неполные месяцы внутри выбранного `report_period` явно отображаются как
  неполные;
- поддерживаются 2 WB кабинета и 2 организации 1С;
- поддерживается FBO и FBS;
- прибыль учитывает эквайринг;
- товарные строки показывают НДС к уплате, исходящий НДС, входящий НДС, НДС
  входящий WB, НДС входящий 1С, расхождение НДС, налог с выручки/НДФЛ,
  налоговый метод, полноту налогового расчета и `прибыль до НДФЛ`;
- товарные строки показывают продажи, возвраты, чистое количество, процент
  возвратов и прибыль до НДФЛ на штуку;
- налоги считаются расчетно по налоговому профилю организации 1С;
- главный лист `Юнит экономика` показывает хранение WB, продвижение WB и налоги
  рядом с прибыльностью товара русскими терминами без технических кодов;
- лист `Ликвидность МД` виден клиенту, не содержит формул и сводных кэшей,
  группирует товары по месяцу и показывает каскад МД1-МД6, прибыль до НДФЛ,
  статус ликвидности, драйвер, статус данных и причину статуса;
- обычный пользователь видит только клиентские вкладки, а технические листы
  скрыты;
- лист `Возвраты` виден клиенту и показывает сумму возвратов, процент
  возвратов, баркод, главную причину и ограничение по источнику причины
  возврата;
- лист `Динамика` виден клиенту и показывает месячную динамику по месяцам
  выбранного `report_period`, явно помечает неполные месяцы и показывает
  изменение месяц к месяцу;
- лист `Расходы WB` виден клиенту и показывает структуру расходов с долей от
  выручки и изменениями месяц к месяцу;
- прочие переменные расходы ОПиУ, кроме налогов, не влияют на прибыль MVP и
  остаются отложенными до отдельного правила распределения;
- хранение и `WB Продвижение` в товарных строках сходятся с недельным
  финансовым отчетом WB, а лист `Распределение расходов` показывает метод и
  статус распределения;
- реклама не влияет на прибыль и видна в Excel как исключенная из MVP;
- недельная динамика заполнена;
- сводки по клиенту, организациям и кабинетам сходятся с dataset;
- ошибки данных видны отдельным листом с русскими статусами и фильтрами;
- витрина `Ликвидность МД` не содержит Excel-ошибок деления на ноль: маржа,
  процент возвратов и МД на штуку остаются пустыми, если знаменатель равен
  нулю;
- топ убыточных товаров сортируется по прибыли до НДФЛ, прибыли на штуку
  и доле возвратов, а также показывает класс убытка;
- аналитика упущенных продаж описана как будущая витрина и не содержит
  расчетных цифр без источника остатков WB;
- повторный запуск на тех же fixtures дает тот же результат;
- workbook не содержит `.env`, токены, API keys, webhook URL или raw secrets.

# Tests

- Unit tests: формула прибыли, отсутствие автоматического legacy fallback,
  приоритет явного профиля 1С над ручным исключением, периоды действия и
  конфликтующие профили, ОСНО с НДС 22/122, входящий НДС, missing input VAT,
  missing tax profile,
  НДФЛ ИП по годовой прогрессивной базе, прибыль до НДФЛ,
  эквайринг, возвраты, себестоимость 1С с уже распределенными допрасходами,
  FBO/FBS, missing mapping, ambiguous mapping, missing cost, реклама excluded,
  partial period/week, продажи, возвраты, чистое количество, процент возвратов,
  распределение хранения и `WB Продвижение` к контрольной сумме недельного WB
  report.
- Source-refresh tests: DB-first builder получает effective tax profiles
  текущего refresh, ручное исключение участвует и в расчете, и в статусе
  `onec_tax_profiles`, а профиль предыдущего refresh не наследуется; VAT-only
  overlay сохраняет P&L, сводит сценарий до копейки, сохраняет настоящий
  `partial` и отклоняет несовместимый grain.
- Contract tests: WB snapshot, 1C cost snapshot, account/org mapping,
  SKU mapping, report dataset.
- Excel smoke tests: workbook opens, sheets exist, summaries reconcile, tables
  and filters exist, `Ликвидность МД` has no formula errors, Russian error
  labels are visible, secrets absent.
- WB Finance tests: mapping new/old field names, `rrdId` pagination, `204`
  stop, 401/403/429 states, decimal parsing.
- Mapping tests: export from mapping service to `sku_mapping`, manual accepted
  priority over automatic candidates, missing mapping, ambiguous mapping,
  excluded mapping, duplicate 1C article, multiple WB skus for one `nm_id`.
- Cost tests: `RecordSet` flattening, provisional fixed receipt candidates,
  missing cost, zero-net sale/return without a false missing-cost blocker,
  ambiguous characteristic.

# Runbook Commands

Выгрузить финансовый факт WB:

```bash
.venv/bin/python scripts/export_wb_finance.py --period-start 2026-03-01 --period-end 2026-06-17
```

Догрузить детализацию по известным недельным reportId WB:

```bash
.venv/bin/python scripts/export_wb_finance_by_report_id.py \
  --report-id 726807272 \
  --report-id 726807263
```

Собрать Excel MVP из последних локальных snapshots:

```bash
.venv/bin/python scripts/build_excel_mvp_from_snapshots.py
```

Загрузить локальный WB Finance snapshot в Postgres:

```bash
.venv/bin/python scripts/load_wb_finance_postgres.py \
  --db-name shumeyko_wb_unit_economics \
  --port 55433 \
  --wb-finance-dir data/wb_finance/<timestamp> \
  --onec-dir data/onec_samples/<timestamp>
```

Собрать Excel MVP из Postgres-слоя:

```bash
.venv/bin/python scripts/build_excel_mvp_from_snapshots.py \
  --wb-finance-source postgres \
  --postgres-db-name shumeyko_wb_unit_economics \
  --postgres-port 55433
```

Собрать DB-first отчет из больших локальных WB snapshot-файлов без удержания
всей детализации WB в памяти:

```bash
.venv/bin/python scripts/rebuild_report_from_sources.py \
  --wb-finance-source files-stream \
  --wb-finance-dir data/wb_finance/<timestamp> \
  --onec-dir data/onec_samples/<timestamp> \
  --onec-services-dir data/onec_marketplace_service_samples/<timestamp> \
  --sales-register-dir data/onec_gross_profit_samples/<timestamp> \
  --tax-system ОСНО \
  --vat-rate 22 \
  --vat-mode included \
  --vat-deduction-mode allowed \
  --revenue-tax-rate 0 \
  --income-tax-kind ip_ndfl_progressive \
  --tax-profile-source accepted-plan:galustov-osno-2026
```

Режим `files-stream` не меняет формулы и read-only границы источников: он
только читает WB raw JSON постранично, раскладывает нормализованные строки во
временные недельные bucket-файлы в локальном ignored cache и считает каждую
пачку существующим расчетчиком. Временный cache удаляется после успешной сборки,
если не указан диагностический флаг `--keep-stream-cache`.

Безопасный режим по умолчанию сохраняет новый report run в статусе staff draft
и не делает его current/published. Явный флаг `--publish` разрешен только после
просмотра расхождений; публикационный барьер повторно проверяет метод P&L,
входящий НДС, себестоимость, обязательные расходы, source lineage и независимые
сверки. При любом блокере публикация завершается конфликтом, а текущая витрина
не переключается.

Явные `--tax-*` параметры разрешены только когда налоговый профиль подтвержден
заказчиком или оформлен как аудируемое ручное исключение. При `--tax-system`
обязательно передается подтвержденный `--vat-deduction-mode`, значение `unknown`
не допускается. Без `--tax-system` сборщик использует только явный профиль из
read-only 1С и не угадывает систему налогообложения.

Сформировать безопасную приемочную сводку по входящему НДС без записи в БД и
без публикации:

```bash
.venv/bin/python scripts/build_tax_input_reconciliation_draft.py \
  --wb-finance-source files-stream \
  --wb-finance-dir data/wb_finance/<timestamp> \
  --onec-dir data/onec_samples/<timestamp> \
  --onec-services-dir data/onec_marketplace_service_samples/<timestamp> \
  --sales-register-dir data/onec_gross_profit_samples/<timestamp>
```

Скрипт пишет только агрегированные Markdown/JSON-файлы в `reports/`:
статусы полноты, `НДС входящий WB`, `НДС входящий 1С`, расхождение и строки
сверки по периоду/кабинету/организации. Raw WB/1C строки, ключи, токены и
исходные документы в эти файлы не включаются.

Загрузить текущие расчетные входы, маппинг и себестоимость 1С, в Postgres:

```bash
.venv/bin/python scripts/load_calculation_inputs_postgres.py \
  --postgres-db-name shumeyko_wb_unit_economics \
  --postgres-port 55433 \
  --wb-finance-dir data/wb_finance/<timestamp> \
  --wb-cards-dir data/wb_product_cards/<timestamp> \
  --onec-dir data/onec_samples/<timestamp> \
  --onec-marketplace-mapping-dir data/onec_marketplace_mapping \
  --sales-register-dir data/onec_gross_profit_samples/<timestamp> \
  --sales-cost-amount-field Себестоимость \
  --snapshot-id <timestamp> \
  --replace-snapshot
```

Собрать Excel MVP полностью из локального Postgres-слоя:

```bash
.venv/bin/python scripts/build_excel_mvp_from_snapshots.py \
  --wb-finance-source postgres \
  --mapping-source postgres \
  --cost-source postgres \
  --postgres-db-name shumeyko_wb_unit_economics \
  --postgres-port 55433 \
  --postgres-snapshot-id <wb-finance-snapshot-id> \
  --mapping-snapshot-id <calculation-inputs-snapshot-id> \
  --cost-snapshot-id <calculation-inputs-snapshot-id>
```

Если `--output` не указан, скрипт перезаписывает один стабильный файл
`reports/shumeyko_wb_excel_mvp.xlsx`. Архивные копии создаются только при
явном указании отдельного `--output`.

Если доступна расширенная OData-выгрузка регистра `Продажи`, стандартная
локальная сборка подхватывает свежий `sales_register.raw.json` автоматически.
Явный параметр нужен только для ручного выбора конкретной выгрузки:

```bash
.venv/bin/python scripts/build_excel_mvp_from_snapshots.py \
  --onec-dir data/onec_samples/<timestamp> \
  --sales-register-dir data/onec_gross_profit_samples/<timestamp> \
  --sales-cost-amount-field Себестоимость
```

Оба скрипта используют только локальный `.env`, не печатают токены и сохраняют
данные в `data/` и `reports/`, которые исключены из Git.
