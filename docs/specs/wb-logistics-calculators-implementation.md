# Статус документа

Статус — `draft`. Это подчинённый design-спек третьей очереди калькуляторов
внутри truth_scope `logistics-cost-analysis`. Канонический документ scope —
accepted
[`docs/specs/wb-logistics-cost-analysis-implementation.md`](wb-logistics-cost-analysis-implementation.md)
(`truth_priority: 100`); при любом расхождении действует он. Draft не является
источником истины (`source_of_truth: false`) и не меняет формулы, классификацию,
финансовый gate первой очереди, состав MVP или границу факт/оценка/гипотеза.

Назначение draft — спроектировать ДО кода два read-only сценарных калькулятора:
логистики и маржинального дохода на единицу. Ключевое ограничение канона:
калькулятор всегда `Оценка`, никогда не подменяет факт, ничего не пишет в WB/1С
и не сохраняется как новая финансовая операция.

Третья очередь по спеку идёт ПОСЛЕ фактического MVP (первая очередь) и во многом
опирается на тарифы и габариты второй очереди (`WP-5 Факторы`, draft
[`wb-logistics-cost-factors-implementation.md`](wb-logistics-cost-factors-implementation.md)).
Переход в `accepted` — после подтверждения доступных официальных тарифов и
подтверждения владельцем набора входов.

# Текущее состояние реализации

Первая очередь (`wb-logistics-v5`) даёт фактические показатели логистики и
детерминированный расчёт юнит-экономики (`src/wb_unit_economics/calculation.py`).
Калькуляторов сейчас нет. Канон резервирует под них метод
`POST /api/reports/{report_id}/logistics/calculate` и метку `Оценка`.
Маржинальный калькулятор переиспользует уже существующий детерминированный
waterfall accepted Excel-методики; логистический калькулятор опирается на тарифы
второй очереди.

# Цель

Дать пользователю сценарный расчёт «что будет, если», не смешивая его с фактом:

1. оценить логистику товара по тарифу, габаритам, весу и сценарным допущениям;
2. посчитать маржинальный доход на единицу по тому же waterfall, что и отчёт, с
   подстановкой сценарных значений;
3. показать сравнение факта выбранного товара и сценария пользователя;
4. явно перечислить использованные допущения и пометить всё `Оценка`.

Калькулятор помогает принять решение (упаковка, цена, склад), но не является
фактом и не меняет отчёт.

# Термины и обязательные трактовки

Термины первой и второй очереди наследуются. Дополнительно:

- `Сценарий` — набор введённых пользователем допущений (тариф, габариты, цена,
  вероятность возврата и т.п.).
- `Оценка` — результат сценарного расчёта. Никогда не подменяет `Факт`.
- `Факт товара` — фактические значения выбранного товара из опубликованного
  отчёта, показываемые рядом со сценарием для сравнения.
- `Диапазон` — интервал оценки при неполных входных данных вместо одного числа.

Текущий тариф и текущие габариты объясняют только сценарий, но не исторический
факт. Исторический период объясняется лишь тарифом/коэффициентом своего периода;
иначе результат помечается `Оценка`.

# Scope

## В scope

- read-only сценарный калькулятор логистики (прямая/обратная/итого) с диапазоном
  при неполных данных;
- read-only калькулятор маржинального дохода на единицу на базе существующего
  waterfall accepted Excel-методики;
- сравнение факта выбранного товара и сценария;
- предзаполнение входов из выбранного товара с возможностью ручной замены;
- явный список использованных допущений и метка `Оценка` во всех выходах;
- метод `POST /logistics/calculate`, выполняющий только расчёт.

## Out Of Scope

Наследует Out Of Scope канона. Дополнительно вне scope:

- любая запись в WB, 1С, банк, CRM, Telegram, email, Bitrix;
- сохранение сценария как новой финансовой операции или изменение отчёта;
- подмена факта оценкой в KPI, рейтингах и рекомендациях;
- объяснение исторического факта текущим тарифом;
- автоматический подбор «оптимальной» цены/склада без явных допущений;
- калькуляторы для Ozon и других маркетплейсов.

# Источники и границы чтения

Калькуляторы не добавляют новых внешних записей и работают поверх уже
сохранённых данных:

- `Факт товара` — из опубликованного `unit_economics_report` и витрин логистики
  первой очереди (read-only).
- Тарифы и коэффициенты — из тарифного snapshot второй очереди (`WP-5`),
  привязанного к периоду. Если тарифный источник недоступен, калькулятор
  использует явно выбранный пользователем тариф и помечает результат `Оценка`.
- Габариты/вес — из витрины `report_logistics_dimension_rows` (`WP-5`) как
  предзаполнение, с ручной заменой.
- Ставки комиссии, хранения, приёмки, продвижения, штрафов, эквайринга и налогов
  для маржинального калькулятора — из той же методики, что и отчёт
  (`calculation.py`), без новых внешних вызовов.

Новые write-методы во внешние системы запрещены. Расчёт не обращается к внешним
API в момент вызова: он использует уже сохранённые snapshot и введённые
пользователем значения.

# Предусловия и проверка готовности

Калькулятор логистики зависит от тарифов второй очереди. Перед включением
подтвердить:

1. доступность тарифов box/pallet за нужный период (probe второй очереди
   подтвердил архив);
2. наличие предзаполняемых габаритов/веса товара (витрина dimensions);
3. соответствие набора входов реально доступным официальным тарифам (канон:
   «набор входов уточняется после проверки доступных официальных тарифов»);
4. что маржинальный waterfall совпадает с методикой отчёта на контрольном товаре.

При отсутствии тарифного источника логистический калькулятор работает только на
явно выбранном тарифе с меткой `Оценка`; маржинальный калькулятор работает
всегда, так как переиспользует методику отчёта.

# Расчётная модель калькуляторов

## Калькулятор логистики

Входы: период тарифа, схема, склад или тарифная зона, габариты с упаковкой, вес,
коэффициент и сценарная вероятность обратной операции. Набор входов уточняется
после проверки доступных официальных тарифов.

Выходы: оценка прямой, обратной и общей логистики; диапазон при неполных данных;
доля в цене/выручке; список использованных допущений. Все выходы помечены
`Оценка`. Обратная часть считается по сценарной вероятности, а не по факту.

## Калькулятор маржинального дохода на единицу

Переиспользует детерминированный waterfall accepted Excel-методики: выручка,
себестоимость, комиссия, хранение, логистика, приёмка, продвижение, штрафы,
эквайринг и применимые налоги. Показывает фактические значения выбранного товара
рядом со сценарием пользователя. Формулы и округление берутся из методики отчёта
и в калькуляторе не переопределяются.

## Общие правила

- Сценарий не сохраняется как финансовая операция и не меняет отчёт.
- Нулевая или отрицательная выручка не приводит к бесконечной доле.
- Неполные входы дают диапазон и явный список недостающих допущений, а не тихий
  ноль.
- Версия методики отчёта и тарифного периода включаются в результат для
  воспроизводимости.

# Хранение сценариев

По умолчанию сценарий не персистится: калькулятор возвращает результат на запрос
без записи. Если позднее потребуется сохранять пользовательские сценарии,
это отдельное additive-решение и отдельная таблица, помеченная как сценарная
(`Оценка`), с tenant isolation и без записи во внешние системы. Витрины факта
первой/второй очереди при этом не меняются.

# API

Additive read-only метод, зарезервированный каноном:

- `POST /api/reports/{report_id}/logistics/calculate` — выполняет только
  сценарный расчёт, не меняет источники и не сохраняет финансовую операцию.

Тело запроса содержит выбранный товар и сценарные входы; ответ содержит оценку,
диапазон, сравнение с фактом товара, список допущений, версии методики и
тарифного периода, а также метку `estimate`. Метод переиспользует авторизацию,
tenant boundary, роли и фильтры кабинета. Инвертированный или невалидный вход
возвращает HTTP 400 без тихой подстановки значений.

# Интерфейс

Калькуляторы — отдельный третий уровень сценария логистики с заметной меткой
`Оценка`, не смешиваемый с фактическим answer-first экраном.

- Входы предзаполняются из выбранного товара, каждый можно заменить вручную;
  изменённое значение визуально отличается от предзаполненного.
- Рядом с оценкой всегда показывается `Факт товара` для сравнения; оценка не
  выдаётся за факт.
- Недостающие входы дают диапазон и явный список допущений, а не одно число.
- Метка `Оценка` присутствует во всех выходах и заголовке блока.
- Калькуляторы доступны за отдельным feature flag после приёмки фактического
  блока; клиентское включение — отдельным решением.

# AI Boundary

Наследует канонический AI Boundary. AI может пересказать допущения и объяснить,
как сценарий отличается от факта; не может объявлять оценку фактом, сохранять
сценарий, менять отчёт/витрины/источники, подставлять отсутствующий вход нулём
или объяснять исторический факт текущим тарифом.

# Ошибки и пограничные случаи

- Нет тарифа за нужный период → расчёт по явно выбранному тарифу с меткой
  `Оценка`; историю им не объясняют.
- Неполные габариты/вес → диапазон и список недостающих допущений.
- Нулевая/отрицательная выручка → доля не уходит в бесконечность.
- Невалидный или инвертированный вход → HTTP 400 без тихой подстановки.
- Попытка сохранить сценарий как факт → запрещена: сценарий не меняет отчёт.
- Валюта первой версии — рубли; иная валюта не определена.
- Расхождение waterfall калькулятора с методикой отчёта → блокирующая ошибка
  сборки, а не молчаливое расхождение.

# Безопасность и tenant isolation

- Каждый запрос ограничен tenant/client/cabinet доступами пользователя.
- Калькулятор read-only: никаких записей в WB, 1С и другие внешние системы.
- Сценарий не сохраняется как финансовая операция; при опциональном хранении —
  отдельная сценарная таблица с tenant isolation.
- Raw payload, токены и секреты не возвращаются интерфейсу и AI.

# Этапы реализации

1. `C-0 Предусловия` — подтвердить доступные официальные тарифы и набор входов;
   зависит от probe второй очереди.
2. `C-1 Маржинальный калькулятор` — переиспользование waterfall методики,
   сравнение факт/сценарий, метка `Оценка` (не зависит от тарифов).
3. `C-2 Логистический калькулятор` — тарифный сценарий, диапазон при неполных
   данных, вероятность обратной операции.
4. `C-3 API и UI` — `POST /logistics/calculate`, третий уровень интерфейса,
   явные допущения.
5. `C-4 Приёмка и rollout` — staff-only за флагом, затем отдельное решение о
   клиентском включении.

Каждый подпакет — за выключенным флагом; расчёт остаётся read-only.

# Acceptance Criteria

Design-часть принята, когда владелец подтвердил набор входов калькулятора
логистики (после проверки доступных тарифов). Реализация готова, когда:

1. оба калькулятора возвращают результат с меткой `Оценка` и списком допущений;
2. маржинальный waterfall совпадает с методикой отчёта на контрольном товаре;
3. рядом с оценкой показан `Факт товара`, и оценка не выдаётся за факт;
4. неполные входы дают диапазон, а не тихий ноль;
5. исторический факт не объясняется текущим тарифом;
6. сценарий не сохраняется как финансовая операция и не меняет отчёт/витрины;
7. пользователь одного tenant не получает данные другого;
8. невалидный вход возвращает HTTP 400 без подстановки;
9. AI не выдаёт оценку за факт и не сохраняет сценарий;
10. ни один сценарий не выполняет запись во внешнюю систему.

# Test Plan

- unit: логистическая оценка (прямая/обратная/итого), диапазон при неполных
  входах, доля при нулевой/отрицательной выручке;
- unit: маржинальный waterfall совпадает с методикой отчёта на фиксированном
  товаре; расхождение → блокирующая ошибка;
- unit: метка `Оценка` и список допущений во всех выходах;
- unit: исторический период → только тариф периода, иначе `Оценка`;
- API: `POST /logistics/calculate` возвращает оценку, сравнение с фактом, версии;
  невалидный вход → HTTP 400; расчёт ничего не сохраняет;
- tenant isolation: недоступность чужих tenant/cabinet;
- инвариант: отчёт и витрины факта не меняются после вызова калькулятора;
- fixtures обезличенные; реальные идентификаторы и объёмы в тесты не переносятся.

Файлы (расширяются существующие): `tests/test_calculation.py`,
`tests/test_logistics_analysis.py`, `tests/test_web_app.py`,
`tests/test_report_marts.py`.

# Rollout And Rollback

1. Подтвердить предусловия `C-0` (доступные тарифы, набор входов).
2. Включить маржинальный калькулятор staff-only за отдельным feature flag.
3. Включить логистический калькулятор после подтверждения тарифов.
4. После приёмки — отдельное решение о клиентском включении.

Rollback отключает метод `calculate` и блок калькуляторов, не изменяя отчёты,
факт и первую/вторую очередь. Калькулятор read-only, поэтому rollback не требует
компенсации внешних записей.

# Предлагаемые решения (на утверждение)

1. Калькулятор — всегда `Оценка`; факт рядом, но не подменяется.
2. Маржинальный калькулятор переиспользует waterfall методики отчёта, не
   переопределяя формулы.
3. Логистический калькулятор зависит от тарифов второй очереди; без них — только
   явный тариф с меткой `Оценка`.
4. Сценарий по умолчанию не сохраняется; опциональное хранение — отдельное
   additive-решение.
5. Исторический факт объясняется только тарифом своего периода.
6. Калькуляторы — отдельный feature flag после приёмки фактического блока.

# Открытые вопросы

- Финальный набор входов логистического калькулятора после проверки доступных
  официальных тарифов.
- Нужно ли сохранять пользовательские сценарии (история «что если»).
- Нужен ли пресет вероятности обратной операции по категории товара.
- Как показывать диапазон при частично доступных тарифах разных периодов.
