# Power BI WB model reference

Этот документ фиксирует безопасную выжимку из ранней Power BI-наработки
`modelWB`. Это ориентир по идеям модели, страницам и формулам Wildberries, а не
источник правды для текущего Shumeyko MVP.

Главный источник правды по расчету остается
`docs/specs/wb-unit-economics-excel-mvp-implementation.md`. Если этот reference
конфликтует с accepted spec, использовать accepted spec.

# Состояние выгрузки

Локальный артефакт лежит в `reports/power_bi_export_input/` и не должен
коммититься. Разбор выполнен по метаданным Power BI Project:

- `modelWB.SemanticModel/model.bim`;
- `modelWB.SemanticModel/diagramLayout.json`;
- `modelWB.Report/report.json`.

Ограничения разбора:

- `model.bim` содержит валидный текст только до первого NUL-блока примерно на
  256 КБ, поэтому полная модель и связи восстановлены не полностью;
- `diagramLayout.json` содержит 20 диаграмм и 50 узлов таблиц, но без явного
  списка relationship-ребер;
- в `report.json` найдено 21 страницa и 201 визуал;
- secret-like строк по словам `password`, `secret`, `token`, `bearer`,
  `authorization`, `api_key` в выгрузке не найдено, но исходный артефакт все
  равно считается локальным и не публикуется.

фиксироваться в коде и `unit_economics_report`, а не жить только в DAX.

# Идеи формул

Ниже формулы приведены как смысловые паттерны. Их нельзя копировать в текущий
расчет без сверки с accepted spec.

## Выручка из финансового отчета WB

В старой модели выручка из `ФинОтчеты` считалась как продажи минус возвраты:

```DAX
ВыручкаЕженОтчет =
  CALCULATE(SUM('ФинОтчеты'[Продажи WB]), 'ФинОтчеты'[Тип  документа] = "Продажа")
  - CALCULATE(SUM('ФинОтчеты'[Продажи WB]), 'ФинОтчеты'[Тип  документа] = "Возврат")
```

Для Shumeyko это совпадает с идеей `net_revenue`, но текущая методика отдельно
ведет `Выручка до СПП`, `СПП` и `Выручка после СПП`.

## Чистое количество

```DAX
Продано шт =
  CALCULATE(SUM('ФинОтчеты'[Количество]), 'ФинОтчеты'[Тип  документа] = "Продажа")
  - CALCULATE(SUM('ФинОтчеты'[Количество]), 'ФинОтчеты'[Тип  документа] = "Возврат")
```

В Shumeyko стоит сохранить явное разделение:

```text
sales_quantity
return_quantity
net_quantity = sales_quantity - return_quantity
```

Это лучше для клиентской сверки и для диагностики возвратов.

## Комиссия WB

Старая модель собирала комиссию из нескольких полей финансового отчета и
вычитала возвраты:

```DAX
Комиссия ВБ с НДС =
  commission_sale_fields_for_sales
  - commission_sale_fields_for_returns
```

Смысловой состав полей:

- вознаграждение WB без НДС;
- эквайринг;
- НДС комиссии;
- вознаграждение/ppvz-поля.

Для текущего проекта важно сохранить прозрачную расшифровку, какие именно поля
WB входят в `wb_commission`, а эквайринг не прятать внутри непонятной общей
комиссии, если accepted spec ведет его отдельной строкой.

## К перечислению

```DAX
К перечислению за товар = [ВыручкаЕженОтчет] - [Комиссия ВБ с НДС]
```

Идея полезна как контрольный показатель WB, но в текущем проекте `К
перечислению WB` не должен подменять прибыль и не должен напрямую сравниваться
с оборотом взаиморасчетов 1С без отдельного источника выплаты.

## Логистика

```DAX
Логистика =
  logistics_amount_where_payment_reason_is_logistics
  - logistics_amount_where_payment_reason_is_logistics_reversal
```

Это хороший паттерн: сторно нужно учитывать отдельной веткой, а не только
суммировать все строки логистики.

## Хранение

```DAX
Хранение =
  CALCULATE(
    SUM('ФинОтчеты'[storage_fee]),
    ALLSELECTED('ФинОтчеты'[Артикул]),
    date_range_filter
  )
```

Идея полезна для периода и фильтров, но в Shumeyko нужно явно фиксировать:

- есть ли товарная детализация хранения;
- если ее нет, каким правилом хранение распределяется по SKU;
- какой статус получает строка при неполной детализации.

## Себестоимость

В старой модели себестоимость бралась через связь с `Номенклатура`:

```DAX
Себестоимость товаровЕж =
  SUMX('ФинОтчеты', [Продано шт] * RELATED('Номенклатура'[Себестоимость.1]))
```

Идея связи товара WB с 1С через номенклатуру правильная, но для текущего проекта
нужны явные статусы:

- `missing_cost`;
- `missing_mapping`;
- `ambiguous_mapping`;
- `needs_review`.

Нельзя молча подставлять ноль или ближайшую себестоимость без статуса.

## Прибыль и маржинальность

Старая модель использовала несколько вариантов:

```DAX
Валовая прибыльЕж = [ВыручкаЕженОтчет] - [СебестПродажМП]
```

```DAX
ПрибыльПр =
  [Валовая прибыльПр]
  - [КомиссWBпр]
  - [ЛогистикаПрод]
  - [НалогУснПр]
  - SUM('Хранение'[Сумма хранения])
  - SUM('СтатистикаРекламыAPI'[ЗатратыРекл])
```

Для Shumeyko это переносится только как структура драйверов:

```text
unit_profit_before_tax =
  revenue_after_spp
  - wb_commission
  - acquiring
  - logistics
  - storage
  - acceptance
  - advertising_if_enabled
  - penalties_and_holdbacks
  - cogs_from_1c
```

В текущем отчете этот операционный слой называется `Управленческая прибыль WB`.
После применения подтвержденного профильного налога клиент видит отдельный KPI
`Прибыль до НДФЛ`. Ни один из этих показателей не является полной `Чистой
прибылью` бизнеса.

## Налоги

В старой модели встречаются разные ставки:

```DAX
Налог УСН = [ВыручкаЕженОтчет] * 0.07
НалогУСНЗак = [Заказано руб] * 0.02
```

Это нельзя переносить в текущий MVP. Действующая рамка определяется налоговым
профилем организации 1С:

```text
revenue_without_vat = revenue_with_vat - vat_output
vat_payable = vat_output - confirmed_vat_input
management_profit_wb =
  revenue_without_vat - cogs_without_vat - wb_expenses_without_vat
profit_before_ndfl = management_profit_wb - confirmed_non_ndfl_income_tax
```

`НДС к уплате` остается отдельной сверкой и не вычитается из P&L повторно.
Без подтвержденного профиля налоговые KPI остаются неопределенными, а формула
`НДС 5/105 + УСН 1%` допустима только для legacy-отчетов с явно закрепленной
старой версией методики.

## СПП и цена после СПП

Старая модель использовала `ЦеныAPI` и `Справочник СПП`:

```DAX
ЦенаССПП =
  IF(
    ISBLANK(SUM('Справочник СПП'[ЦенаСПП])),
    SUM('ЦеныAPI'[ЦенаСоСкид]),
    SUM('Справочник СПП'[ЦенаСПП])
  )
```

Идея fallback понятна, но в текущем MVP нельзя скрыто подставлять СПП. Если
подтвержденного источника СПП нет, отчет должен показывать ограничение источника
и не выдавать подстановку как факт.

## Возвраты

```DAX
Возврат шт = CALCULATE(SUM('ФинОтчеты'[Количество]), 'ФинОтчеты'[Обоснование оплаты] = "Возврат")
%Возвратов = DIVIDE([Возврат шт], [Продано шт])
```

Для Shumeyko лучше хранить возвраты положительным количеством и считать
процент возвратов только если продажи не равны нулю.

## ABC

Старая модель использовала классический подход:

```DAX
Рейтинг по выручке =
  RANKX(ALL('Номенклатура'[Артикул]), [ВыручкаПр], , DESC, Dense)

ABC по выручке =
  SWITCH(
    TRUE(),
    [Накопительный итог доли по выручке] <= 0.8, "A",
    [Накопительный итог доли по выручке] <= 0.95, "B",
    "C"
  )
```

Это хороший кандидат для следующих версий отчета: ABC по выручке, прибыли и
потерям. Для MVP не должен блокировать базовую юнит-экономику.

## Остатки и подсорт

В модели есть блоки:

- `Остат.ВБ шт.`;
- `Остатки дома`;
- `ВсегоОстаток`;
- `Обор-ть дн.`;
- `Сред.продажи в день`;
- `ПодсортВБ`;
- `Остаток к моменту поступления`.

Идея полезна для будущего операционного модуля:

```text
days_of_stock = wb_stock_quantity / average_daily_sales
replenishment_need = max(target_stock_days * average_daily_sales - wb_stock, 0)
```

В текущем Shumeyko MVP это отдельный слой, не часть базовой прибыли.

## Реклама

В модели есть отдельные `_Меры_Рекл`, `СтатистикаРекламыAPI`,
`СПР рекламные компании`, показатели CTR/CPC/стоимость корзины/стоимость заказа
и расход рекламы.

Для Shumeyko это полезный следующий слой:

- реклама может быть включена в прибыль только если источник и атрибуция
  подтверждены;
- расходы без SKU-атрибуции должны получать отдельный статус или
  распределяться по принятому правилу;
- AI-summary может объяснять рекламные драйверы, но не должен придумывать
  атрибуцию.

# Что стоит забрать в проект

1. Карта доменов WB шире, чем текущий MVP: фин. отчет, продажи, заказы,
   остатки, цены/СПП, реклама, карточки, конкуренты, ABC.
2. В модели полезно иметь отдельный слой `_Меры`, но в нашем продукте формулы
   должны быть воспроизводимы в коде и тестах.
3. Для клиента важны страницы `Юнит-экономика`, `Финансовый отчет`, `Продажи`,
   `Возвраты`, `Остатки`, `Цены и СПП`.
4. Для консультанта полезны расширения: реклама, ABC, конкуренты, карточки,
   план-факт и подсорт.
5. Сторно и возвраты должны считаться отдельными ветками, а не теряться в общей
   сумме.
6. Показатели СПП нужно показывать отдельно и не сравнивать WB-выручку после СПП
   с общей выручкой 1С/ОПиУ без пояснения.

# Что нельзя переносить как есть

- Нельзя считать Power BI-модель источником правды для текущего MVP.
- Нельзя переносить hardcoded-ставки `7%`, `2%`, фиксированные `20` рублей или
  иные параметры без accepted spec.
- Нельзя называть показатель полной `Чистой прибылью`, если не учтены все
  расходы бизнеса и налоговые корректировки.
- Нельзя молча подставлять ноль, fallback или ближайшую себестоимость без
  статуса качества данных.
- Нельзя оставлять расчет только в DAX: формулы должны быть покрыты тестами и
  воспроизводиться из snapshots, mapping и версии методики.
- Нельзя подключать Power BI напрямую к raw snapshots или секретным источникам
  клиента.

# Следующие действия

- При расширении accepted spec добавить отдельный backlog-блок:
  `Power BI reference ideas`.
- Для рекламы, ABC, остатков и конкурентов заводить отдельные спецификации или
  разделы acceptance criteria.
- Если нужна полная реконструкция отношений модели, повторно выгрузить `.pbip`
  после сохранения Power BI Desktop, чтобы `model.bim` был валидным JSON без
  NUL-хвоста.
